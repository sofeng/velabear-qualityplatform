# TestHub 后续实施方案

本文档用于明确当前阶段的后续工作顺序、目标、范围、交付物和验收标准。目标不是并行堆功能，而是先建立稳定基线，再逐步提升部署效率、前端架构一致性和 AIOps 闭环能力。

编制日期：`2026-04-26`

## 1. 总体目标

后续工作分四个主阶段推进：

1. 建立可回退的代码与部署基线
2. 将版本迭代部署改造成快速发布通道
3. 将【AI用例生成】模块重构为类似【思源研发管理】的层次式标签页工作台
4. 实现【AI自动部署】MVP，并逐步接入现有 AI 研发与测试链路，形成 AIOps 闭环

## 2. 总体原则

### 2.1 先做基线，再做重构，再做新能力

当前仓库处于明显的混合状态：

- 已有部署与离线交付相关改动
- 已有业务模块改动
- 已有本地打包产物和本地运行产物
- 已有未入库的 migrations

如果不先做基线整理，后续的快速部署、前端架构改造、AI 自动部署都会被脏工作区放大风险。

### 2.2 先做部署提速，再做大功能扩展

本次离线部署首次打通链路花费较长时间，核心原因是第一次补齐完整交付链路。后续版本迭代不能再重复这个成本。部署提速必须先于 AI 自动部署能力建设，否则 AI 开发速度会被发布速度卡住。

### 2.3 前端改造先抽公共壳，不逐页复制

【思源研发管理】当前已具备工作台入口和 query/tab 驱动形态。后续【AI用例生成】模块改造，必须先抽象公共工作台壳层，再迁移页面，避免重复造轮子。

### 2.4 AI 自动部署先做 MVP，不直接做全量生产版

第一版只面向测试环境、模板化部署、受控目标环境，先打通最小闭环。等链路稳定后，再扩到审批、回滚、门禁、多环境、多模板。

## 3. 推荐执行顺序

后续严格按以下顺序推进：

1. Phase 1：基线整理与本地 Git 基线提交
2. Phase 2：快速迭代部署能力建设
3. Phase 3：AI 模块层次式标签页重构
4. Phase 4：AI 自动部署 MVP 落地

不建议跳过 Phase 1 或把 2、3、4 并行硬推。

## 4. Phase 1：基线整理与本地 Git 基线提交

### 4.1 目标

形成一个清晰、可回退、可继续开发的本地 Git 基线版本，为后续所有工作提供锚点。

### 4.2 主要工作

#### A. 清理和隔离本地产物

明确哪些内容不应入库：

- 离线打包目录，如 `.offline_bundle/`
- 中间 staging 目录，如 `.bundle_stage/`
- 本地环境文件，如 `frontend/.env.local`
- 本地运行数据库和缓存状态文件
- 仅用于本机调试的产物

#### B. 明确基线提交范围

建议将“当前应提交内容”和“当前不提交内容”分开：

应提交：

- 本次部署相关代码、脚本、Compose、Dockerfile、文档
- 初始化导入导出脚本
- 当前有效的业务代码修改
- 必须纳入版本控制的 Django migrations

暂不提交或单独处理：

- `.env` 实际环境值变更
- 本地打包产物
- 本地运行数据
- 敏感 seed 运行时导出内容
- 平台资料目录下尚未明确是否纳入版本库的脑图/资料文件

#### C. 修正版本控制边界

需要落实：

- `.gitignore` 收敛本地产物
- migrations 不再被错误忽略
- 敏感或生成式 seed 产物不直接进源码仓库

#### D. 提交基线

建议至少形成两个 commit：

1. 代码与部署基线 commit
2. 文档与 Prompt 模板 commit

如有必要，再补一个 tag：

- `baseline/offline-deploy-20260426`

### 4.3 交付物

- 干净的 `.gitignore`
- 明确的基线提交范围
- 本地 Git 基线 commit
- 可选 tag

### 4.4 验收标准

- `git status` 中只剩明确有意保留的未提交内容
- 本地打包产物不再污染工作区
- migrations 进入可控版本管理
- 基线 commit 可作为后续所有开发的回退点

## 5. Phase 2：快速迭代部署能力建设

### 5.1 目标

将后续版本迭代部署，从“重复走完整离线部署大流程”，改造成“可快速发布、快速验证、快速回滚”的标准通道。

### 5.2 核心问题

当前首次部署花时间，主要因为：

- 第一次梳理依赖和初始化链路
- 第一次设计离线部署结构
- 第一次验证远端环境约束
- 第一次修复真实运行问题

这些工作后续不应重复。

### 5.3 目标状态

后续版本发布应收敛为：

1. 本地构建变更镜像
2. 仅导出必要镜像
3. 更新 release 元数据
4. 上传增量包
5. 远端 `docker load`
6. 定向重建变更服务
7. 自动执行 smoke 验证
8. 失败可快速回滚

### 5.4 主要工作

#### A. 固化发布目录与运行结构

保持以下结构长期稳定：

- 运行目录
- Compose 文件
- `.env`
- 数据持久化目录
- 日志目录

不要每次版本发布都改目录结构。

#### B. 建立镜像版本规范

建议统一使用：

- 发布日期
- 提交 SHA
- 构建序号

例如：

- `20260426`
- `20260426-1`
- `20260426-2`
- `20260426-gitsha`

#### C. 实现增量发布机制

核心思想：

- 前端没变，不重发前端镜像
- MySQL、Redis 基础镜像没变，不重发
- 仅变更后端时，只更新后端镜像和相关服务

#### D. 标准化初始化与升级

拆分为：

- 首次初始化
- 常规升级发布
- 强制重建
- 回滚发布

#### E. 自动化发布与验证脚本

建议形成：

- 本地打包脚本
- 上传脚本
- 远端发布脚本
- smoke 验证脚本
- 回滚脚本

### 5.5 交付物

- 快速发布说明文档
- 标准镜像版本规范
- 增量发布脚本
- smoke 验证脚本
- 回滚方案

### 5.6 验收标准

- 后续版本迭代不再重复完整首发流程
- 单服务变更可独立发布
- 发布流程可以半自动或一键化执行
- 发布失败能快速恢复

## 6. Phase 3：AI 模块层次式标签页重构

### 6.1 目标

把【AI用例生成】模块下所有菜单页和子功能页面，重构成类似【思源研发管理】的层次式标签页工作台。

### 6.2 当前判断

仓库中已存在可借鉴基础：

- 路由入口已以 `/manual-testcases/list` 为统一工作台入口
- query 参数驱动 tab 切换
- 页面已在单工作台中承载多个业务子页

这意味着后续应优先复用该思想，而不是把 AI 菜单逐页改成多个零散页面。

### 6.3 主要工作

#### A. 抽象公共工作台壳层

建议先抽出一个可复用的壳层组件，例如：

- `ModuleWorkspaceShell`
- `ModuleTabWorkspace`

统一承载：

- 顶部主标签
- 二级标签或内容区域
- query 参数同步
- 权限过滤
- 页面缓存策略

#### B. 梳理 AI 模块信息架构

将【AI用例生成】相关能力整理为清晰的层级结构，例如：

- 需求分析
- 用例生成
- AI 开发
- 自动执行
- 缺陷联动
- 回归验证
- 配置管理
- 执行记录

#### C. 路由改造

将 AI 模块入口改为类似：

- 单入口工作台路由
- query 驱动子页面
- 兼容旧链接跳转

#### D. 组件迁移

按照“先壳层、后页面”的方式迁移：

1. 先做空壳
2. 再迁移单个标签页
3. 再迁移二级功能
4. 最后清理旧入口

### 6.4 交付物

- 公共工作台壳层组件
- AI 模块新的层次式标签页入口
- 兼容旧链接的路由跳转
- 页面迁移清单

### 6.5 验收标准

- AI 模块入口结构统一
- 标签切换稳定且可直达
- 权限控制不退化
- 不因重构破坏现有业务能力

## 7. Phase 4：AI 自动部署 MVP 落地

### 7.1 目标

新增平台级【AI自动部署】能力，补上 AIOps 闭环中“自动部署”这一环，但第一版仅做测试环境、模板化、可审计的 MVP。

### 7.2 产品定位

不建议把它仅做成【AI用例生成】模块下一个普通页面。

更合理的定位是：

- 前台入口可以挂在 AI 工作台中
- 底层能力必须是平台级部署能力
- 可与 AI 开发、自动测试、缺陷、工作流统一集成

### 7.3 MVP 范围

第一版建议只支持：

- 测试环境
- Docker Compose 模板化部署
- 受控服务器目标
- 指定目录结构
- 指定环境变量模板
- 自动 smoke 验证
- 自动回归触发

暂不直接做：

- 生产环境自动发布
- 任意命令执行
- 任意服务器自由部署
- 多种复杂编排系统

### 7.4 主要工作

#### A. 数据模型

建议新增以下核心实体：

- `DeploymentTarget`
- `DeploymentTemplate`
- `BuildArtifact`
- `DeploymentExecution`
- `DeploymentApproval`
- `RollbackRecord`

#### B. 执行引擎

执行层建议基于现有异步任务体系扩展：

- Celery 执行部署任务
- 通过 SSH 或容器代理执行受控命令
- 支持日志流与状态回传

#### C. 工作流集成

与现有 `workflow` 集成，形成状态流转，例如：

- 待部署
- 构建中
- 部署中
- 冒烟验证中
- 回归测试中
- 已通过
- 已失败
- 已回滚

#### D. 与现有模块打通

与以下能力建立联动：

- AI 需求分析
- AI 开发
- API 自动化
- UI 自动化
- 缺陷管理
- 质量分析

#### E. 安全与审计

必须具备：

- 受控部署模板
- 受控部署目标
- 凭据隔离
- 操作日志审计
- 高风险环境审批

### 7.5 交付物

- AI 自动部署 MVP 数据模型
- 后端 API
- 部署执行任务
- 日志与状态展示
- 与测试链路联动的最小闭环

### 7.6 验收标准

- AI 开发成果可自动部署到测试环境
- 部署结果可回传平台
- 可自动触发 smoke 或回归
- 失败可进入缺陷/修复链路
- 全流程可追踪、可审计

## 8. 各阶段之间的依赖关系

### 8.1 Phase 1 是后续所有工作的前提

如果基线不清晰：

- 快速部署会被脏工作区污染
- AI 模块前端重构难以隔离风险
- AI 自动部署开发缺少稳定起点

### 8.2 Phase 2 是 Phase 4 的基础能力

如果版本发布仍然很慢：

- AI 开发再快也无法快速闭环
- AI 自动部署会沦为“自动执行低效流程”

### 8.3 Phase 3 和 Phase 4 可以部分交叉，但不应同时大规模落地

建议顺序：

- 先完成 AI 工作台壳层设计
- 再落 AI 自动部署页面与状态展示

## 9. 风险点

后续推进中需要特别注意：

- `.env` 等敏感配置不应误入库
- seed 运行时数据不应直接提交
- migrations 必须纳入治理，否则部署仍不稳定
- 平台资料目录下的脑图和资料文件需单独判断是否纳入版本管理
- 前端工作台重构不能影响现有权限和 query 直达能力
- AI 自动部署必须先受控，不能变成任意远程执行器

## 10. 当前建议的立即动作

在你下达下一步指示后，建议从以下动作开始：

1. 完成 Phase 1 的基线范围确认
2. 完成本地 Git 基线提交
3. 进入 Phase 2，设计快速发布通道

## 11. 本方案的执行方式

后续执行时遵循以下原则：

- 每一阶段开始前先说明本阶段目标
- 每一阶段先做边界确认，再做落地
- 每一阶段都形成中间交付物
- 未经明确指示，不跨阶段并行推进

## 12. Phase 2 新增补充：双通道快速发布

Phase 2 现已从单一“离线增量 bundle”扩展为双通道：

1. offline bundle
2. registry fast release

执行原则：

- offline bundle 负责首次部署和离线兜底
- registry fast release 负责后续高频迭代

这项补充不会改变 Phase 2 的阶段目标，只是把“快速发布”从半增量推进到真正可层复用的增量发布。

新增交付物应纳入 Phase 2：

- `deploy/REGISTRY_FAST_RELEASE.md`
- `deploy/release/build_registry_release.ps1`
- `deploy/release/publish_registry_release_remote.ps1`
- `deploy/release/rollback_registry_release_remote.ps1`
- `deploy/release/remote_apply_registry_release.sh`
- `deploy/release/remote_rollback_registry_release.sh`
- `deploy/release/bootstrap_registry_remote.ps1`
- `deploy/release/remote_bootstrap_registry.sh`
