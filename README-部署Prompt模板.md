# 项目部署 Prompt 模板

本文档基于本次 TestHub 平台离线容器化部署过程沉淀，目标是提供一份“小白也能复用”的通用部署 Prompt 模板。使用者只需要替换项目名、目录、服务器信息、部署要求，即可将其应用到自己的项目部署场景中。

## 1. 这次部署沉淀出的核心经验

### 1.1 先梳理项目真实依赖，再谈部署

很多部署失败，不是 Docker 没写对，而是一开始就没有搞清楚：

- 哪些服务是平台运行必需的
- 哪些服务只是增强功能依赖
- 哪些服务只是开发调试时需要
- 哪些配置存在数据库里
- 哪些配置还散落在代码、环境变量、后台页面、媒体目录中

部署前如果不把这些问题梳理清楚，后面就会不断出现“服务看起来启动了，但功能不能用”的问题。

### 1.2 不要把“启动成功”误认为“部署完成”

真正的部署完成，至少应该确认：

- 前端可访问
- 后端 API 存活
- 管理后台可访问
- 管理员账号可登录
- 数据库正常
- Redis 正常
- 后台任务服务正常
- 初始化数据已导入
- 核心业务链路能跑通

只看 `docker ps` 是远远不够的。

### 1.3 初始化数据不能只看数据库

很多业务配置虽然对平台运行至关重要，但并不一定天然都在数据库中，例如：

- 版本配置
- 第三方接口配置
- URL 前缀配置
- 邮件模板
- 目录树
- 媒体目录中的基础资源

要交付一个真正可迁移、可复用、可自动初始化的平台，必须把这些内容统一纳入初始化数据体系。

### 1.4 远端部署优先使用离线镜像方案

如果项目对源码敏感，或者目标服务器不稳定、不能联网、不能安装构建依赖，那么应优先使用以下方案：

1. 本地构建镜像
2. 本地打包镜像
3. 上传到服务器
4. 远端 `docker load`
5. 使用 `docker-compose` 启动

这样可以避免：

- 源码泄露
- 远端构建失败
- 构建依赖缺失
- 网络波动导致拉包失败
- 线上环境与本地环境不一致

### 1.5 持久化目录必须统一规划

持久化目录必须提前规划好，并且不要散落到宿主机不同位置。至少要统一管理以下数据：

- 数据库数据
- Redis 数据
- 媒体文件
- 静态文件
- 日志
- 应用内部状态文件

如果容器能重建，但数据不丢，部署才算合格。

### 1.6 后台任务系统必须单独验收

很多项目首页能打开，但后台异步任务、定时任务、消息队列消费实际是坏的。对于有 Celery、RQ、Sidekiq、队列消费者、调度器的项目，必须单独验证：

- worker 是否稳定运行
- 是否有缺失依赖
- 是否能连到消息中间件
- 是否能访问它需要的宿主资源
- 关键任务是否真正可执行

### 1.7 验收之后要做善后

部署完成后，还需要：

- 清理远端已上传源码
- 删除临时 tar 包
- 保留运行目录和数据目录
- 输出访问清单
- 输出账号密码清单
- 输出启停命令
- 输出日志排查命令
- 输出最终交付文档

否则交付并不完整。

## 2. 适用场景

这份 Prompt 适用于以下项目：

- 前后端分离项目
- Django / Flask / FastAPI / Node.js / Java / Go 等后端项目
- 带 MySQL / PostgreSQL / Redis / MQ 的业务系统
- 带初始化数据、字典、模板、配置项的平台类项目
- 需要 Docker 化部署的项目
- 需要离线部署的项目
- 不允许源码长期驻留在服务器的项目

## 3. 使用方式

### 3.1 使用前需要准备的信息

在使用下面的 Prompt 前，你至少需要准备这些信息：

- 项目名称
- 本地源码目录
- 目标服务器 IP
- SSH 用户名
- SSH 密码或密钥
- 服务器操作系统
- 服务器是否已安装 Docker / Docker Compose
- 是否允许源码上传到服务器
- 是否要求离线部署
- 持久化根目录
- 部署根目录
- 是否需要保留现有数据库数据作为初始化数据
- 是否允许清理历史临时文件和源码

### 3.2 推荐使用方式

建议把这份 Prompt 直接发给具备以下能力的 AI 代理：

- 能读取本地代码
- 能执行终端命令
- 能修改文件
- 能 SSH 到目标服务器
- 能构建 Docker 镜像

如果 AI 没有执行权限，也可以要求它先产出完整的部署脚本、目录结构、seed 方案和交付文档。

## 4. 小白可直接复用的完整部署 Prompt

将下面方括号中的内容替换为你自己的项目参数后，直接使用。

```text
你现在是我的资深 DevOps / 后端交付工程师 / 容器化部署专家，请基于当前项目代码和服务器环境，直接帮我完成“从分析到交付”的完整部署工作。不要只停留在建议层面，请主动检查、修改、构建、打包、部署、验证，并在每个关键阶段给我明确结论。除非遇到高风险或必须确认的事项，否则不要频繁反问我。

【项目基本信息】
- 项目名称：[填写项目名]
- 本地源码目录：[填写源码目录]
- 目标服务器 IP：[填写服务器IP]
- SSH 用户名：[填写用户名]
- SSH 密码或密钥：[填写密码/说明密钥]
- 服务器操作系统：[如 CentOS 7 / Ubuntu 22.04]
- 服务器已具备 Docker / Docker Compose 能力：[是/否]
- 是否允许把源码上传到服务器：[是/否，建议填 否]
- 是否要求离线部署（本地打包镜像，远端 docker load）：[是/否]
- 持久化根目录：[如 /AIOps/data/my-project]
- 部署根目录：[如 /AIOps/apps/my-project-offline]
- 是否需要保留现有数据库数据并作为初始化数据：[是/否]
- 是否需要清理服务器上与本次部署无关的历史包、临时文件、源码：[是/否]
- 是否存在端口占用风险，需要先检查并避让：[是/否]

【我的目标】
我要把这个项目做成一个真正可交付、可重复部署、可迁移的小白可用部署方案。你必须覆盖以下内容：
1. 梳理项目真实依赖，识别“平台运行必需服务”和“完整功能依赖服务”，明确哪些必须启动，哪些可选。
2. 列出所有服务的访问地址、端口、账号、密码、用途，形成清单。
3. 检查项目是否存在未自动执行的 migration、初始化脚本、首次启动依赖、后台任务依赖、外部服务依赖。
4. 检查哪些配置和初始化数据在数据库里，哪些不在数据库里；凡是属于平台运行必须的配置、模板、目录树、字典项、业务初始化数据，都要尽量落到数据库或 seed 中。
5. 如果项目当前有“手工在后台配过，但代码和数据库里没有闭环”的内容，必须指出，并设计补齐方案。
6. 为项目生成适合生产交付的 Dockerfile、docker-compose、env、init、seed、导入导出脚本。
7. 如果我要求离线部署，你必须在本地构建镜像、docker save 打包、上传到远端、docker load、再通过 compose 启动；不要在远端直接用源码 build，除非我明确允许。
8. 所有运行期数据必须持久化到我指定的目录，至少要覆盖数据库、缓存、媒体文件、静态文件、日志、应用状态目录。
9. 初始化流程必须幂等：首次部署能自动初始化，重复重启不会反复污染数据。
10. 部署完成后必须验证前端、后端、数据库、缓存、后台 worker、关键任务链路，而不是只看容器是否启动。
11. 部署完成后要清理源码和临时包，避免泄露；但不能误删业务数据和运行目录。
12. 最终必须输出完整交付文档，适合小白接手运维。

【你必须按这个顺序工作】

第一阶段：项目与依赖盘点
- 先阅读代码和配置，不要先假设。
- 梳理项目架构：前端、后端、数据库、缓存、消息队列、任务服务、文件存储、第三方接口、管理后台。
- 明确：
  - 平台最低可运行所需服务
  - 完整功能所需服务
  - 开发环境专用服务
- 输出一份服务矩阵，说明每个服务的用途、是否必需、默认端口、依赖关系。

第二阶段：初始化与数据盘点
- 检查 migration、fixtures、seed、管理命令、首次启动脚本。
- 找出所有“必须作为初始化数据交付”的内容，包括但不限于：
  - 平台管理员账号
  - 基础字典、菜单、权限、角色、组织、目录树
  - 版本配置
  - 第三方接口配置
  - URL 前缀配置
  - 邮件模板
  - 业务默认配置
  - 媒体/静态资源中必须交付的内容
- 明确哪些已在数据库，哪些还没落库。
- 对未落库但必须交付的内容，优先改造为落库或 seed 化；如果确实不能落库，明确说明原因，并给出文件级导入方案。
- 生成初始化数据清单和导出/导入脚本。

第三阶段：部署方案设计
- 根据项目实际情况设计容器化方案，不要套模板。
- 处理这些关键问题：
  - 端口冲突
  - 环境变量
  - 数据卷持久化
  - SELinux / AppArmor
  - 首次初始化与重复启动分离
  - 后台 worker 与主服务拆分
  - 健康检查
  - 日志目录
- 如果后台任务依赖 Docker、浏览器、外部二进制、系统库，必须补齐依赖，并在容器内验证。

第四阶段：远端部署前检查
- 登录目标服务器，检查：
  - Docker / Compose 是否可用
  - 磁盘空间是否足够
  - CPU / 内存是否能支撑
  - 目标端口是否被占用
  - 目录权限
  - SELinux / 防火墙状态
  - 现有同机服务冲突风险
- 如果发现冲突，不要硬上默认端口，要主动改成安全、不冲突的新端口。
- 不要影响服务器上与本项目无关的已有服务。

第五阶段：构建、打包、上传、部署
- 如果要求离线部署：
  - 本地构建所有所需镜像
  - docker save 导出镜像包
  - 将运行时小包和镜像大包分开打包
  - 上传到服务器
  - 在服务器 docker load
  - 使用 compose 启动
- 如果不允许源码上服务器：
  - 远端只能保留运行目录、compose、env、seed、镜像和持久化数据
  - 部署完成后清理源码和临时构建文件
- 初始化成功后，要生成清晰的部署目录结构。

第六阶段：验收与问题修复
- 验收必须至少覆盖：
  - 前端访问
  - 登录页访问
  - 管理后台访问
  - 后端 API 存活
  - 管理员账号登录成功
  - 数据库连接成功
  - Redis 连接成功
  - 后台 worker 稳定运行
  - 关键异步任务链路可用
  - 初始化数据已导入
- 不要只看 `docker ps`。
- 如果日志报错，要继续追到根因并修复。
- 常见错误包括：
  - 迁移未执行
  - 语法错误
  - 缺少 Python/Node/系统依赖
  - 卷权限问题
  - 端口冲突
  - 后台 worker 缺依赖
  - 容器内访问宿主能力缺失
- 修复完成后再次验证，直到形成闭环。

第七阶段：交付物输出
- 最终必须给我以下成果：
  1. 服务清单
  2. 访问地址清单
  3. 账号密码清单
  4. 初始化数据清单
  5. 部署目录清单
  6. 数据持久化目录清单
  7. 一键启停命令
  8. 日志查看命令
  9. 常见故障排查命令
  10. 风险与后续优化建议
  11. 一份可直接交付给小白运维的 README 文档

【工作要求】
- 每开始一个阶段，都先告诉我你要做什么。
- 发现问题不要停在“分析”，要继续修。
- 除非高风险，不要等我一句一句批准。
- 不要偷懒用想当然的方式回答，必须结合代码、配置、日志、服务器现状。
- 如果你引用“今天、当前、最新”，请给出明确日期。
- 对任何账号、端口、目录、镜像标签，都给出精确值。
- 不要用破坏性命令删除不相关数据。
- 如果需要清理文件，先确认目标路径确实属于本项目部署范围。
- 最终回答时，先给我结论，再给证据，再给文档位置。

现在开始工作。第一步先盘点项目结构、依赖和真实必需服务，不要直接假设。
```

## 5. 小白使用建议

### 5.1 如果你是第一次部署项目

建议你先不要要求 AI “直接上线”，而是明确告诉它：

- 先盘点项目结构
- 先列出服务依赖
- 先列出初始化数据
- 先设计部署方案
- 再执行部署

这样能避免 AI 一上来直接写 Dockerfile，结果方向错了。

### 5.2 如果你担心源码泄露

在 Prompt 中明确写：

- 不允许源码上传到服务器
- 必须本地构建、远端离线加载镜像
- 部署完成后清理远端临时包

### 5.3 如果你担心数据丢失

在 Prompt 中明确写：

- 数据目录必须统一持久化到指定根目录
- 容器重建不能丢数据
- 初始化必须幂等
- 不能误删运行中项目的数据目录

### 5.4 如果你担心 AI 只会说不会做

在 Prompt 中明确要求：

- 不要停留在建议层面
- 遇到问题继续修
- 除非高风险，不要频繁反问
- 最终给出可执行命令和交付文档

## 6. 推荐补充项

如果你的项目更复杂，可以在 Prompt 中继续补充这些内容：

- 是否需要 HTTPS / Nginx / 反向代理
- 是否需要域名绑定
- 是否需要对象存储
- 是否需要定时备份数据库
- 是否需要 CI/CD
- 是否需要监控、告警、日志采集
- 是否需要灰度发布或回滚方案

## 7. 最终目标

这份 Prompt 的目标，不是让 AI 给你一堆部署建议，而是让 AI 形成一套完整交付闭环：

- 先分析清楚
- 再设计方案
- 再执行部署
- 再完成验收
- 再输出文档

如果这五步没有全部完成，就不算真正完成部署。
