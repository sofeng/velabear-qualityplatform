## 2. 后续总体目标

Phase 5 至 Phase 8 的总目标不是继续堆页面，而是完成从“AI 开发成果”到“自动部署、自动验证、自动回滚、自动提缺陷、自动修复建议”的真实闭环。

后续总体目标分为四步：

1. 把 Phase 4 的控制面接到 Phase 2 的真实发布执行层
2. 把 AI 开发、构建制品、部署、测试、缺陷串成闭环
3. 把执行链条纳入工作流和审批约束
4. 在稳定链路基础上增加 AI 运维智能决策能力

## 3. 总体原则

### 3.1 不重造执行层

后续所有“自动部署 / 自动回滚 / 自动冒烟 / 自动回归”能力，必须直接复用 Phase 2 已有的脚本与发布结构，不允许再发明第二套发布体系。

### 3.2 先接通，再闭环，再智能

优先级严格如下：

1. 先把真实执行层接通
2. 再把研发测试链路串起来
3. 再把审批与流程约束补齐
4. 最后做 AI 智能判断与建议

### 3.3 默认只面向测试环境自动执行

在 Phase 5 和 Phase 6 阶段：

- 默认只允许测试环境自动发布
- 预发和生产必须先保留审批和人工门禁
- 不允许平台变成任意 SSH 命令执行器

### 3.4 控制面与执行面分离

前端页面负责：

- 配置
- 触发
- 状态查看
- 审计追踪

执行逻辑必须落在后端服务层和受控脚本层，不在前端拼装执行逻辑。

## 4. Phase 5：接通真实发布执行层

### 4.1 目标

把 Phase 4 的 `DeploymentExecution` 从“计划与记录对象”升级为“可真实驱动发布脚本的执行对象”。

### 4.2 核心问题

当前平台已经知道：

- 发布到哪里
- 用什么模板
- 发布哪些组件
- 用哪种发布通道
- 是否需要审批

但还没有真正做到：

- 自动调用本地发布脚本
- 自动触发远端 apply
- 自动执行 smoke
- 自动写回实际执行结果

### 4.3 范围

本阶段只做真实执行接通，不做全链路智能化。

需要完成：

- 建立部署执行适配层
- 复用 `deploy/release` 下现有脚本
- 支持 `registry` 与 `offline_bundle` 两种通道
- 支持动作：
  - `prepare`
  - `publish_apply`
  - `smoke`
  - `rollback`
- 执行日志、结果摘要、远端路径、冒烟结果回写
- 增加测试环境自动执行开关
- 增加失败重试和人工回滚入口

不做：

- 生产环境自动发布
- 任意远端命令执行
- 多集群 / Kubernetes / Helm 等新编排体系

### 4.4 建议实现结构

建议新增或完善以下结构：

- `apps/deployments/executors/`
- `apps/deployments/services/dispatch_service.py`
- `apps/deployments/services/log_service.py`
- `apps/deployments/tasks.py`

执行层职责建议如下：

- Executor：根据 `release_mode` 选择具体发布通道
- Dispatcher：根据 `DeploymentExecution` 生成执行任务
- Task：交给 Celery 异步执行
- Log Service：管理日志摘要与可追踪信息

### 4.5 交付物

- 真实执行适配器
- Celery 执行任务
- 发布日志回写机制
- smoke 结果回写机制
- 失败 / 重试 / 回滚的最小闭环
- 对应后端测试

### 4.6 验收标准

- 平台中创建一条 `DeploymentExecution` 后，能真实执行测试环境发布
- `registry` 通道能走通正常发版
- `offline_bundle` 通道仍可作为兜底
- smoke 失败时能回写失败状态
- 回滚动作能触发 Phase 2 的回滚脚本并回写记录
- 全过程可追踪、可审计

## 5. Phase 6：打通 AI 研发闭环

### 5.1 目标

把 “AI 开发 -> 构建制品 -> 自动部署 -> 自动冒烟 -> 自动回归 -> 自动提缺陷” 串成完整研发闭环。

### 5.2 核心问题

当前模块之间是可并存的，但还不是一条自动传递的链路：

- AI 开发任务和发布制品没有自动对接
- 发布成功后不会自动触发 API/UI/回归测试
- 测试失败后不会自动进入缺陷闭环

### 5.3 范围

本阶段重点是模块联动，不扩展新的底层执行体系。

需要完成：

- `AIDevelopmentTask` 与 `BuildArtifact` 建立映射关系
- AI 开发完成后可自动或半自动生成制品记录
- 制品记录可一键创建 `DeploymentExecution`
- 发布成功后自动触发：
  - API 自动化
  - UI 自动化
  - 回归测试
- 测试失败后自动生成缺陷草稿或缺陷记录
- 缺陷与发布记录、测试记录、AI 开发任务互相关联

### 5.4 关键设计

建议新增或补充以下关联字段：

- `AIDevelopmentTask.release_tag`
- `BuildArtifact.source_task`
- `DeploymentExecution.source_ai_task`
- `DeploymentExecution.source_requirement`
- `DeploymentExecution.regression_result`
- `DeploymentExecution.defect_sync_status`

### 5.5 交付物

- AI 开发与制品生成联动
- 制品到部署执行联动
- 发布成功后的自动测试触发器
- 测试失败后的缺陷联动器
- 研发闭环追踪字段与查询接口

### 5.6 验收标准

- 从一个 AI 开发任务可以追踪到对应制品和部署记录
- 部署成功后可自动触发测试
- 测试失败后可自动生成缺陷记录
- 单条需求至少能串起：
  - AI 需求分析
  - AI 开发
  - 制品
  - 部署
  - 冒烟
  - 回归
  - 缺陷

## 6. Phase 7：工作流化与审批化

### 6.1 目标

把“可以执行”升级为“受控执行”，让部署链路进入平台级流程治理。

### 6.2 核心问题

如果没有工作流约束，后续随着 AI 自动能力增强，系统会出现：

- 状态跳跃
- 审批缺失
- 回滚无审计
- 人工干预不可追踪

### 6.3 范围

本阶段以 `workflow` 模块集成为主，不扩展新的业务域。

需要完成：

- 设计部署工作流状态机
- 将 `DeploymentExecution` 纳入工作流
- 支持审批、驳回、转人工、重试、回滚、重新发布
- 区分测试 / 预发 / 生产环境治理规则
- 增强操作审计

### 6.4 建议状态流

建议状态流如下：

1. 待构建
2. 已生成制品
3. 待部署
4. 待审批
5. 部署中
6. 冒烟中
7. 回归中
8. 已通过
9. 已失败
10. 已回滚
11. 待修复
12. 修复后待重发

### 6.5 交付物

- 部署工作流定义
- 审批流页面或审批动作接口
- 工作流和部署执行对象的关联字段
- 审计日志增强
- 高风险环境门禁规则

### 6.6 验收标准

- 同一条部署任务不能绕过状态机乱跳
- 预发 / 生产环境默认需审批
- 所有审批、驳回、回滚、重试动作有审计日志
- 可根据状态自动路由到后续修复或重发流程

## 7. Phase 8：AI 自动化运维智能能力

### 7.1 目标

在执行链条稳定后，增加真正可用的 AI 运维智能决策能力。

### 7.2 核心问题

如果前面 Phase 5 至 Phase 7 没有完成，AI 只能做“猜测性建议”；只有真实执行记录、日志、测试结果、缺陷结果都沉淀下来，AI 才有可靠输入。

### 7.3 范围

本阶段只在已有真实数据基础上做智能建议，不让 AI 直接越权执行。

需要完成：

- AI 生成发布建议
- AI 推荐发布通道：
  - `registry`
  - `offline_bundle`
- AI 分析冒烟失败原因
- AI 分析回归失败原因
- AI 生成回滚建议
- AI 生成缺陷草稿
- AI 生成修复与重发建议

### 7.4 建议能力入口

建议在 AI 工作台的“自动化运维”分组中逐步增加以下能力：

- 发布建议
- 风险评分
- 日志归因
- 回滚建议
- 重发建议
- 缺陷建议

### 7.5 交付物

- AI 运维建议服务
- 风险评分模型或规则引擎
- 失败日志归因摘要
- 回滚建议面板
- 修复后重发建议面板

### 7.6 验收标准

- AI 能基于真实发布记录给出结构化建议
- AI 输出能关联到真实任务、日志、结果和缺陷
- AI 默认只做建议与辅助决策，不默认直连高风险执行

## 8. 推荐执行顺序

后续实施顺序必须严格如下：

1. Phase 5：接通真实发布执行层
2. Phase 6：打通 AI 研发闭环
3. Phase 7：工作流化与审批化
4. Phase 8：AI 自动化运维智能能力

不建议跳过 Phase 5 直接做后续阶段，原因很明确：

- 不接通执行层，后续所有自动部署都只是“记录型功能”
- 不完成闭环联动，自动测试、自动缺陷、自动修复都无法真实串起来
- 不完成流程约束，后续 AI 运维能力会缺少安全边界

## 9. 每阶段执行前置条件

### 9.1 Phase 5 前置条件

- Phase 2 脚本链路稳定
- 测试环境可访问
- Registry 通道可用
- Celery worker 可用
- 凭据引用机制边界明确

### 9.2 Phase 6 前置条件

- Phase 5 已能真实发版
- 自动化测试触发接口可用
- 缺陷模块可接收联动写入

### 9.3 Phase 7 前置条件

- Phase 6 链路稳定
- 工作流规则已具备可维护的配置入口
- 审批参与角色边界清晰

### 9.4 Phase 8 前置条件

- 前三阶段已产生足够真实运行数据
- 日志、执行结果、缺陷记录结构化程度足够
- AI 输出边界和审计要求已明确

## 10. 明确不在本轮规划内的内容

以下内容不属于当前 Phase 5 至 Phase 8 的直接落地范围：

- 重新设计新的部署体系
- 引入 Kubernetes / Helm / ArgoCD
- 把平台改造成通用远程运维平台
- 默认开启生产环境自动发布
- 去除人工审批和门禁

## 11. 建议的实际推进方式

后续执行时建议每个阶段都按以下节奏推进：

1. 先补阶段文档和边界说明
2. 再补后端基础结构和测试
3. 再补前端入口和最小交互
4. 再做联调验证
5. 最后再做本地 Git 提交

这样可以保证每一阶段结束时都具备：

- 可解释
- 可验证
- 可回退
- 可继续叠加

## 12. 当前结论

基于当前已完成的 Phase 1 至 Phase 4，后续最关键、最不能跳过的阶段是：

- Phase 5：接通真实发布执行层

只有这一阶段完成后，后面的 AI 自动部署、自动回归、自动缺陷、自动修复，才会从“规划能力”变成“真实闭环能力”。
