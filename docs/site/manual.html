01产品是什么

BearAI 的「AI 会话开发」不是普通的聊天窗口，而是围绕真实软件研发过程组织的 AI 工作台。 你输入的每一句需求、上传的每个文件、AI 产出的每份需求条目 / 业务逻辑图 / 原型 / 测试用例 / 代码， 都会被绑定到同一个「会话」中，可随时回看、复用与验收。

💬

一句话即可开始

不需要先写完整 PRD。可从一句话、一个用户故事、一份已有原型或普通对话开始，平台逐步补全。

🔗

全链路可追溯

按「项目澄清→需求澄清→需求分析→业务逻辑→原型→测试→实现」组织流程，每步产物被下一步复用。

✅

可验收可交付

会话详情页保留需求基线、业务逻辑、原型、测试、设计风格、代码与运行预览，便于验收与迭代。

一句话记住它：把 AI 会话当成一个「有记忆、有产物、有流程」的研发助理，而不是一次性问答的聊天机器人。

02核心概念速览

动手前先认识 6 个贯穿全程的概念，后面每一步操作都会用到。

概念它是什么你会在哪里用到
会话一次完整 AI 研发过程的载体，含输入、产物与配置，有唯一 ID。在「AI 产品」页发送需求后自动创建。
会话类型决定在什么场景下开启、走多深的自动化流程，共 5 种。输入区左下角「会话类型」按钮选择。
会话环境AI 实际运行、生成代码和文件的执行环境，默认「本地会话环境」。输入区「会话环境」按钮选择。
模型驱动会话的大模型或 Codex CLI 引擎，决定生成质量与能力。输入区「模型选择」按钮选择。
工具箱能力可挂载到会话的专业能力：Prompt / Skill / Agent / Flow / MCP / Tool。输入区「工具箱能力」按钮勾选。
产物 / 基线AI 产出并沉淀的结构化结果，如需求基线、业务逻辑图、原型、测试、代码。会话详情页各工作区页签查看与验收。

03进入 AI 产品入口

AI 会话开发的统一入口是左侧导航的「AI 产品」页面。进入后可见顶部需求输入区，及下方历史产品会话卡片。

  1. 打开「AI 产品」页面在左侧导航进入「AI 产品」。确保已登录，页面会自动加载会话环境、模型和历史产品。
  2. 认识输入区页面中央是大输入框，下方一排圆形按钮就是本次会话的全部配置项（环境、模型、会话类型、工具箱、文件、研发对象）。
  3. 查看已有产品输入区下方按类型分类展示历史会话卡片，可直接点击进入继续。
安全提示：体验环境请勿上传或生成涉密、敏感、商业机密内容。如需安全处理企业数据，请在「本地会话环境」中操作。

04会话类型详解（最关键的一步）

「会话类型」代表不同场景下开启的会话：它决定你的输入成熟度、平台自动化深度，以及会话打开后默认进入的工作区。点击输入区左下角「会话类型」按钮切换，共 5 种。

会话类型适合谁 / 何时用典型输入平台会做什么
对话探索、咨询、分析资料、临时调用能力。一个问题、一段资料、一个文件、一段代码。保持通用 AI 对话，可手动挂载 Prompt/Skill/Agent/MCP/文件/研发对象，不强制走链路。
一句话需求只有用户故事，但需要专业需求分析结果。「作为客服主管，我希望看到超时未处理反馈，以便及时催办。」把故事拆成角色、目标、对象、规则、异常与验收标准，沉淀为需求澄清与基线分析。
一句话生成应用希望快速得到可运行产品。「做一个客户反馈管理系统，支持提交反馈、客服处理、分类统计。」自动串联全链路：项目澄清→需求澄清→基线分析→业务逻辑→原型→测试→产品实现。
从需求澄清开始已有初步需求，想直接确认与基线化。需求片段、会议纪要、待确认需求清单。直接进入需求澄清工作区，打磨 / 重写 / 接受 / 不接受，再生成脑图、业务逻辑、原型和测试。
已有原型图已有 Axure、HTML 原型、截图或页面说明。原型 ZIP、HTML、截图、页面目录或交互说明。优先从原型解析页面、组件、入口、状态与业务流，再生成原型需求分析、测试分析和业务逻辑。
怎么选？一句话决策：只想咨询 → 对话；只有一句故事 → 一句话需求；想最快产出系统 → 一句话生成应用；已有需求文字 → 从需求澄清开始；已有原型 → 已有原型图。

05输入区配置项逐个说明

输入框下方那排圆形按钮就是发送前的全部配置。以下按从左到右顺序说明，前三项（环境、模型、会话类型）通常保持默认即可。

按钮作用建议
🖥️ 会话环境选择 AI 运行、生成代码和文件的执行环境。默认「本地会话环境（local-default）」。一般保持默认；处理敏感数据务必用本地环境。
⚙️ 模型选择选择驱动会话的模型引擎，含普通大模型与 Codex CLI 类模型（用于真实生成代码 / 应用）。生成应用 / 原型 / 代码优先选 Codex CLI 类模型。
🔑 授权类型仅选中 Codex 模型时出现。API Key / ChatGPT 登录 / Access Token。按管理员配置的凭据方式选，默认 API Key。
⏱️ 速度仅选中 Codex 模型时出现。快速 / 均衡 / 深入 / 最强，越往后思考越充分、耗时越长、质量越高。探索用「均衡」，重要交付用「深入 / 最强」。
💬 会话类型本次会话的场景类型，共 5 种。最重要的选项。务必按输入成熟度正确选择。
🔧 工具箱能力按 6 类分组勾选本轮要启用的专业能力，右上角数字为已选数量。按需选择，避免一次挂载过多导致上下文过载。
📁 选择文件附带本地文件作上下文，支持 PDF/Word/TXT/MD/HTML/图片/ZIP/Excel/PPT，单次最多 6 个。需求文档、原型 ZIP、参考资料均可，平台自动提取文本。
🔗 选择 AI 研发对象引用已有会话的工作区产物（项目基线、需求、原型、测试、代码等）作本轮上下文。做二次迭代或跨会话复用时非常有用。
➤ 生成 / 发送创建会话并进入会话详情页开始执行。需已填内容、选好环境和模型；也可按 Enter 发送。
已选中的配置会以「标签」形式显示在输入框下方，每个标签右侧有 × 可随时移除，发送前可再次确认。

06五分钟快速上手

以「一句话生成应用」为例，走一遍从想法到可预览应用的最短路径。其它类型步骤类似，只是自动化深度不同。

  1. 进入「AI 产品」并输入需求如「做一个客户反馈管理系统，支持提交反馈、客服处理、分类统计」。需求越具体（业务对象、角色、动作、统计目标），后续澄清越少。
  2. 选择会话类型为「一句话生成应用」点击「会话类型」按钮选中它，此类型会自动串联整条研发链路。
  3. 确认环境与模型会话环境保持「本地会话环境」；模型建议选 Codex CLI 类，并按需设置授权类型与速度。
  4. 点击「生成」发送平台创建会话并跳转到会话详情页（CodexChat 工作区），开始逐阶段执行。
  5. 观察左侧研发链路执行依次显示项目澄清、需求澄清、基线分析、业务逻辑、原型、测试、产品实现各阶段的状态。
  6. 按产物验收切到右侧各工作区页签，先确认需求澄清和业务逻辑，再看原型、测试、设计风格，最后在「产品预览」查看结果。

07研发链路与执行状态

无论哪种研发型会话，背后都遵循同一条研发链路。理解它，你就知道每一步在做什么、产出什么、从哪里验收。

阶段 1项目澄清范围、角色、业务对象、规则与风险。
阶段 2需求澄清拆成可接受 / 不接受的结构化条目。
阶段 3基线需求分析页面、功能、原子功能与测试种子。
阶段 4基线业务逻辑流程、状态、数据流与权限。
阶段 5原型设计可预览 HTML 原型。
阶段 6测试分析测试矩阵与自动化用例。
阶段 7产品实现真实代码与运行预览。

不同会话类型走多长的链路

会话类型覆盖阶段是否自动
一句话生成应用阶段 1 → 7（全链路）全自动
一句话需求阶段 1 → 7，强调先澄清后生成半自动
从需求澄清开始阶段 2 → 7（跳过项目从零发散）半自动
已有原型图原型解析 → 基线分析 → 业务逻辑 → 测试 → 实现半自动
对话不强制链路，按需调用能力手动

如何读懂执行状态

已完成   进行中   失败   等待中

某一阶段失败不影响前序产物。「产品实现」失败时，前面的需求澄清、业务逻辑、原型、测试产物依然有效、可复用。查看失败卡片的 AI 消息、代码预览和工作区文件定位原因，修正后重试。

08会话详情工作区（10 个页签）

需求需求澄清、基线需求分析、基线业务逻辑把需求从口语描述推进到结构化基线、脑图和可编辑业务逻辑图。
原型预览AI 原型、Axure 原型查看 AI 生成或导入的原型，作为需求、测试和开发依据。

测试设计测试分析、自动化测试用例生成等价类、边界值、状态转换、权限、异常、数据一致性等测试设计。

09需求澄清操作（核心体验）

需求澄清是本平台最核心的体验之一。它不是让 AI 写一段说明，而是把需求拆成一条条可选择、可编辑、可追踪、可验收的结构化条目，由你逐条确认后沉淀为需求基线，供后续所有环节复用。

单条需求上的操作

🔧 打磨

让 AI 在当前条目基础上做更细拆解，产出更细的子需求或补充验收点。适合把粗需求变精。

♻ 重写

用 AI 重新生成替换当前条目。适合当前条目方向不对、需整体改写时使用。

✅ 接受需求

确认该需求。接受后成为后续基线分析、业务逻辑、原型、测试和实现的稳定输入。

🚫 不接受需求

排除该需求。保存基线时被剔除，避免无依据功能进入实现。

批量操作

勾选多条需求后可进行批量打磨 / 批量重写 / 批量接受，适合把用户故事、会议纪要、业务描述一次性整理成需求基线。

从「只有一个用户故事」开始的推荐流程

  1. 选择「一句话需求」会话类型输入用户故事，如「作为客服主管，我希望查看超时未处理反馈，以便及时催办」。
  2. 让 AI 拆解故事平台识别角色、业务目标、触发条件、业务对象、页面功能、规则、异常和验收标准。
  3. 在需求澄清中逐条确认对拆出的条目逐项打磨、重写、接受或不接受，把口语化故事变成专业需求。
  4. 生成基线分析和测试种子接受后的需求进入基线需求分析，用于生成页面功能、原子功能、追踪矩阵和测试点。
验收要点：确认需求都来自当前会话输入，没有 AI 凭空新增的「幻觉需求」；同时检查是否覆盖角色、对象、规则、异常和验收标准。发现问题就用「重写」或「不接受」处理后再往下走。

10基线需求分析与业务逻辑

需求被接受后，平台把它转化成两类结构化产物：基线需求分析（页面 / 功能 / 测试种子）和基线业务逻辑（业务流程与状态图）。它们是原型、测试和代码实现的直接输入。

基线需求分析

  • 页面节点：系统包含哪些页面。
  • 功能节点 / 原子功能：每个页面下的功能，及不可再拆的最小功能单元。
  • 原子测试种子：从原子功能派生的最小测试关注点。
  • 追踪矩阵：需求 → 功能 → 测试的对应关系，保证不漏不错。

基线业务逻辑

生成当前系统真实业务的流程图，通常含业务流程、状态流转、数据流、权限矩阵与异常补偿。

常见问题：业务逻辑图内容不对。先检查图中业务对象和页面是否来自当前会话。若出现历史系统内容（如无关的示例系统），说明生成时读错了上下文——重新触发「基线业务逻辑」，并明确要求读取当前会话的项目 / 需求基线。

11原型与测试设计

写代码之前，平台先产出可预览的原型和测试设计，让你在实现前就能检查页面结构和质量覆盖，把问题拦在最前面。

原型预览

在「原型预览」页签查看 AI 生成的 HTML 原型（或导入的 Axure 原型）。用它检查：页面是否齐全、字段是否完整、操作入口是否清晰、状态和提示是否能支撑核心业务流。

测试设计

  • 测试分析：从等价类、边界值、状态转换、权限、异常、数据一致性等维度生成的测试分析矩阵与原子测试点。
  • 自动化测试用例：可用于自动化执行（如 Playwright）的测试用例草案。
验收要点：确认测试是否覆盖等价类、边界值、状态转换、权限、异常和数据一致性；每个测试点最好只验证一个条件，粒度太粗时可在测试分析中继续细化原子测试点。

12设计风格：把视觉约束带入开发

「设计风格」页签位于「产品预览」之前，用于在写代码前确定页面视觉风格。开发时 AI 会读取所选风格档案，把 Design Token、页面模板和视觉验收要求写入实现要求，保证界面统一、专业。

内置风格档案

企业稳健

研发平台 / 质量平台 / 管理后台。低噪声、表格可扫描、操作路径明确，是默认风格。

工程深色

面向开发工具、控制台类深色界面。

金融精密

面向数据运营、金融类高信息密度界面。

清爽协作

面向协作、效率类轻量清爽界面。

AI 实验室

面向 AI 产品、前沿科技感界面。

Design Token 与页面模板

每个风格档案都带一组 Design Token（主色、辅助色、强调色、界面底色、圆角、密度、字体等），以及可覆盖的页面模板（登录页、工作台、列表页、详情 / 表单页、数据看板、移动端等）和质量门禁（设计 Token 一致、桌面 / 移动端自适应、Playwright 截图验收、文字不溢出不重叠等）。

操作步骤

  1. 选择风格按软件类型选：管理后台优先「企业稳健」，数据运营选「金融精密」，开发工具选「工程深色」。
  2. 查看 / 微调 Token 与模板在页签中预览页面效果、核对色彩与密度，按需调整。
  3. 保存设计档案保存后在当前会话及后续开发环节复用，形成可追踪的项目设计基线。开发环节会据此生成界面。
用「一句话生成应用」时，如果没有单独选择风格，平台会自动使用默认的「企业稳健」设计档案，保证生成结果依然规整。

13产品预览与代码

研发链路走到最后，平台会生成真实代码并尝试启动预览服务。你可以在这两个页签查看最终成果。

产品预览页签

显示生成应用的运行预览。卡片和页签会标注「产品服务在线 / 服务不在线 / 检测中」。在线时可点击进入或复制预览地址分享。

代码预览页签

查看会话生成的源代码文件内容。当产品实现失败时，可结合代码预览与工作区文件定位构建、启动或运行错误。

预览打不开怎么办？查看左侧研发链路的失败卡片、AI 消息、代码预览和工作区文件，通常是容器、依赖、端口或构建的问题。修正后可重新触发产品实现，前序产物不受影响。

14工具箱能力（Prompt / Skill / Agent / Flow / MCP / Tool）

AI 会话可从工具箱按需挂载不同类型的专业能力。能力不是越多越好，建议按当前任务选必要能力，避免上下文过载。点击输入区「工具箱能力」按钮，能力按下面 6 种类型分组展示。

Prompt（提示词）

固定格式的分析、总结、审查、生成任务。如「需求分析 Prompt」「用例生成 Prompt」。

Skill（技能）

带规则、步骤和输出合约的专业能力。如「缺陷分析 Skill」、各阶段官方研发 Skill。

Agent（智能体）

需要决策、检查、串联多步动作。如「Playwright 测试 Agent」、源头门禁 Agent。

Flow（流程）

固定流程编排。如「AI 研发闭环 Flow」「AI 自动部署 Flow」。

MCP（上下文接入）

让 AI 安全读取外部或平台上下文。如「平台上下文 MCP」，只读接入需求、任务、缺陷、部署。

Tool（工具动作）

执行具体动作。如平台查询、AI 需求创建、AI 开发任务执行、AI 部署执行等。

能力上的两个标记：风险等级与仅随本轮

标记含义
low / medium / high 风险等级标识能力的操作风险。high 风险（如直接执行、部署类）请谨慎启用，确认影响后再使用。
仅随本轮提示该能力尚未通过审核或不可长期绑定，只作为本轮提示的一部分临时生效，不会持久绑定到会话。
只有已启用且已审核通过的能力才会持久绑定到会话；其它仅在当前这一轮发送时携带。能力的创建、审核和上架由「AI 军火库 / 能力市场」管理，普通使用者按需勾选即可。

15附带文件与引用 AI 研发对象

除了文字需求，你还能给会话补充两类上下文：本地上传的文件，以及已有会话沉淀的研发产物。

选择文件（📁）

  • 支持 PDF、Word、TXT、Markdown、HTML、图片（PNG/JPG）、ZIP/TAR/RAR、Excel、PPT 等格式。
  • 单次最多附带 6 个文件；平台自动为需求文档提取文本作上下文。
  • 原型类文件（HTML、ZIP 等）会被自动标记为「原型」，其它标记为「其它」。

选择 AI 研发对象（🔗）

点击后打开「选择本轮上下文」弹框，按项目 / 需求 / 原型预览 / 原型需求分析 / 测试设计 / 设计风格 / 产品预览 / 工作区 / 代码预览 / 上传文件分类，引用其它会话已生成的产物（如某个需求基线、某张业务逻辑图、某份测试用例、某段代码）作本轮上下文。

典型用法：二次迭代。新建一个「对话」或「从需求澄清开始」的会话，引用上一版应用的需求基线或代码，就能在已有成果上继续改进，而不用从零开始。

16结果验收清单

企业级 AI 开发不能只看「有没有生成页面」。建议按下面 6 层逐层验收，任何一层不通过都回到对应环节修正后再往下走。

验收层检查什么不通过时怎么处理
需求层需求是否都来自当前会话输入？有无凭空新增？是否覆盖角色、对象、规则、异常和验收标准？回到需求澄清，重写或不接受错误需求，再重新生成后续产物。
业务逻辑层流程图是否描述当前系统真实业务？是否含状态流转、权限、异常和补偿？重新生成基线业务逻辑，并要求读取当前项目 / 需求基线。
原型层页面、字段、操作、状态和提示是否能支撑核心业务流？回到原型或需求澄清补充页面与交互，再更新测试设计。
测试层是否覆盖等价类、边界值、状态转换、权限、异常和数据一致性？在测试分析中继续细化原子测试点，避免一个测试点验证多个条件。
风格层界面是否符合所选设计风格、Design Token、页面密度和视觉验收要求？回到设计风格页签重新选择或保存档案，再让开发环节修正。
运行层产品预览是否可访问？容器、数据库、接口和持久化是否正常？查看产品实现日志、代码预览和工作区文件，定位构建、启动或运行错误。

17常见问题与处理

提示"加载工具箱能力失败"

通常是能力资产或会话环境接口临时加载失败。先确认登录态有效，点击「重试」；若只影响能力列表，可继续查看已生成产物。

提示"加载会话环境失败"

会话环境加载失败会影响环境、模型和上下文选择。重新进入「AI 产品」页或会话详情页，确认当前会话环境仍存在后点击「重试」。

突然跳到登录页

多数与本地登录凭据被清空或刷新失败有关。重新登录后再打开多个页签验证；同一浏览器应共用一套登录态。

业务逻辑图 / 需求内容不对

检查产物中的业务对象和页面是否来自当前会话。若混入历史系统内容，回到对应环节重新生成，并要求读取当前会话基线。

产品实现失败 / 预览打不开

查看左侧链路失败卡片、AI 消息、代码预览和工作区文件。失败不影响前序产物继续复用，修正后重试即可。

不知道从哪种会话类型开始

只想咨询选「对话」；只有一句故事选「一句话需求」；想最快产出系统选「一句话生成应用」；已有需求文字选「从需求澄清开始」；已有原型选「已有原型图」。

「生成」按钮点不了

需同时满足：输入框有内容、已选会话环境、已选模型。三者齐全后按钮才亮起，也可在输入框内按 Enter 发送。

能力太多，该选哪些

研发型会话已自动带上该场景所需的官方能力，通常无需手动加。只有做特定动作（如查询平台、创建需求、执行部署）时才按需补选。

术语解释

原子功能 / 原子测试点不可再拆分的最小功能单元 / 最小测试关注点。
