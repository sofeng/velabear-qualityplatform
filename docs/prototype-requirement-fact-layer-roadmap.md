# 原型需求分析与可用性验证 P0-P4 规划

## 背景与目标

平台后续要把 Axure 原型、文字需求、红色标注、弹窗提示、字段、状态、权限等信息转化为可被 AI 编码、业务逻辑建模和浏览器验证共同使用的工程化输入。脑图适合人阅读，但不适合作为唯一事实源；因此先建立轻量“需求事实层”，再在其上生成脑图、业务图和验证任务。

## 总体原则

- 不把某一个原型页面写死为规则，所有能力按页面结构、控件语义、需求文字、视觉证据、业务动作和触发关系抽象。
- 脑图、业务图、测试验证都作为事实层的不同视图，避免各模块各自理解需求。
- P0 先基于当前列表类页面能力落地 MVP，后续随着 Skill 对更多页面类型的解析能力提升持续补充事实类型和关系。
- 先保证“能追溯、能展示、能被下游消费”，再逐步追求覆盖率和推理深度。

## P0：需求事实层 MVP

目标：在官方原型需求分析产物中新增结构化事实层 JSON/Graph，使每个关键页面信息都能以机器可消费的事实记录存在，并能反挂到脑图节点。

范围：

- 页面上下文事实：原型目录、页面标题、菜单路径、页签、组织/数据范围控件。
- UI 解构事实：功能板块、控件、筛选字段、列表字段、行操作、更多操作菜单、提示框/弹窗。
- 文字需求事实：需求说明片段、分类、匹配节点、匹配置信度、证据来源。
- 视觉证据事实：红色文字、红框、强调标注及对应节点。
- 可验证提示：事实类型、操作入口、字段/选项/默认状态、预期检查点。

交付：

- `requirement_facts` 输出到官方原型分析 `sections`、`workspace_artifacts.structured_data`、`downstream_inputs`。
- 脑图节点携带与自身相关的 `requirement_facts`。
- 右侧节点详情面板增加两个顶部 Tab：`节点详情` 和 `需求事实`。
- 后端单元测试覆盖事实生成、节点反挂、下游产物输出。
- 42080 环境真实浏览器验证：新会话生成脑图，选中节点可看到对应事实。

## P1：AI 可用性验证闭环

目标：让 AI 不只根据脑图节点做人工式遍历，而是根据事实层生成可执行验证任务，通过浏览器逐项验证开发后软件功能是否真实可用。

范围：

- 基于事实层生成功能验证任务：输入、选择、点击、弹窗、列表、状态、权限、异常提示。
- 基于业务逻辑图生成流程验证任务：主流程、分支流程、状态流转、角色协作、异常补偿。
- 建立验证结果回写：通过/失败、失败截图、失败节点、事实 ID、业务图节点 ID、复现步骤。
- 支持“脑图视图”和“业务图视图”定位失败来源。

依赖：

- P0 提供稳定事实层。
- P2 提供业务逻辑多图和流程模型。

## P2：原型业务逻辑多图

目标：基于 P0 事实层和原型需求脑图，生成更专业的业务逻辑视图，而不是只停留在页面元素解构。

优先图谱：

- 业务流程图：页面操作、触发条件、弹窗、结果状态。
- 状态流程图：字段状态、记录状态、审批状态、同步状态等生命周期。
- 权限图/权限矩阵：角色、组织范围、按钮权限、数据范围、无权限提示。

扩展图谱：

- 角色协作图。
- 数据流图。
- 异常补偿图。
- 接口/外部系统交互图。

交付：

- 新增或增强官方 Skill，用于从事实层生成业务逻辑模型。
- 调用平台既有 draw.io/MCP 绘图方案产出可编辑图。
- 图节点保留事实 ID 追溯关系，支持跳回需求脑图节点。

## P3：页面呈现与目录治理

目标：让原型需求分析、事实层、业务逻辑图和验证结果在页面上形成统一的可导航结构。

建议：

- 左侧增加原型目录结构，以原型目录/页面为基础组织。
- `原型需求分析` 页面和 `原型业务逻辑` 页面共用同一套目录。
- 脑图节点、事实记录、业务图节点、验证任务之间建立跳转与反向定位。
- 事实层默认不作为主页面大面积展示，只在节点详情、调试视图、导出产物和验证报告中呈现。

## P4：通用能力加固与持续回归

目标：持续提升 Skill 对不同原型页面类型、不同设计风格和不同需求说明写法的泛化能力。

页面类型覆盖：

- 列表查询类页面。
- 表单新增/编辑类页面。
- 审批流/状态流转类页面。
- 看板/仪表盘类页面。
- 详情页/主子表页面。
- 配置类页面。
- 多角色权限类页面。

工程机制：

- 建立原型页面类型覆盖矩阵。
- 每新增一种页面类型，沉淀最小样例、事实层期望、脑图期望、业务图期望、验证任务期望。
- 建立回归集，防止某次 Skill 优化只改善一个页面却破坏其他页面。
- 对事实层质量增加评分：覆盖率、挂载率、证据追溯率、低置信度项、未匹配需求说明。

## 推荐实施顺序

1. P0：先落地需求事实层 MVP 和右侧 Tab 展示。
2. P2：基于事实层生成核心业务逻辑图。
3. P1：把事实层和业务逻辑图组合为浏览器验证闭环。
4. P3：统一目录、跳转、追溯和页面呈现。
5. P4：长期持续扩展页面类型和回归能力。

这个顺序的核心原因是：P0 解决“需求事实可被机器稳定读取”，P2 解决“业务场景和流程可被机器理解”，P1 再把两者合并为真实软件可用性验证。
