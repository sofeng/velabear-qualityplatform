AI研发平台 · 完整规划

三条用户业务场景、三个智能体、DSL 工程化与 Skill 工厂工作规划

本规划将 Axure 导入企业研发、人机协同自动研发、全自动行业产品生成三条入口明确拆开，同时把 TestHub AI RD DSL 升级为贯穿需求、原型、流程、测试、代码、部署、治理和 Skill 生成的工程语义契约。行业模板与快速出成品能力采用平台内置入口、独立 Skill Runtime、可插拔外部底座适配的组合；企业原型编辑器 DSL 不属于本规划范围。

版本：v1.1 日期：2026-06-01 主线优先级：To B Axure 导入企业研发优先 交付形态：单页 HTML 文档

0.1 规划结论

平台需要形成三条清晰入口，而不是把所有能力放在一个页面内平铺。三条入口可以共用底层 DSL、AI 会话、工作区治理、AI 开发、自动化测试和 Harness 交付能力，但产品入口、用户路径、智能体编排、权限与交付门禁必须分开。

P0企业主线

Axure/Figma/HTML 已有原型导入，转成 TestHub AI RD DSL，经确认后进入需求追溯、测试、开发、Harness 部署。这是 To B 主打核心竞争力。

P1人机协同自动研发

一句话需求，人工澄清项目和需求，平台自动需求分析、原型、开发、测试、部署。适合有明确项目意向、愿意沟通确认的用户。

P2全自动行业产品

用户只给行业或通用软件方向，由 AI 自动澄清、套行业模板、生成成品。当前 AI 会话已有部分能力，但需要更强模板、门禁和沙箱治理。

核心判断：DSL 优化不是独立功能，而是三条业务场景的共同工程底座。没有 DSL，智能体只能输出文本和代码；有了可校验、可版本化、可追溯的 DSL，平台才能做到企业级可控、可审计、可交付。
行业模板与 Skill 判断：场景三的快速出成品能力应采用“平台内置入口 + 独立 Skill Runtime + 可插拔 Skill Adapter”的组合。平台掌握业务场景、项目资产、DSL、权限、审计和交付，生成引擎与外部低代码底座通过服务化和插件化接入，避免主平台变成某个低代码产品的二次封装。

0.2 优先级原则

优先级 业务判断 工程判断 结果要求
P0 企业客户已经有需求基线和 Axure 原型，最愿意为导入、追溯、开发、测试、部署闭环付费。 先补齐 DSL 底座、导入确认、版本基线、追溯、Harness 交付，避免功能散乱。 形成可演示、可试点、可签约的企业级主线。
P1 人机协同自动研发适合个人、创业团队、小型内部系统，移动端入口价值明显。 复用 P0 DSL 与 Agent 编排，新增项目/需求澄清卡片、移动端流程和自动开发串联。 形成 To C/轻量团队产品化入口。
P2 全自动行业产品具备想象空间，但对模板库、质量门禁、行业资产依赖最高。 必须建立行业 DSL 模板、沙箱隔离、自动评测和发布审核后再扩大。 形成行业软件工厂，不影响 P0/P1 稳定性。

1.1 三条业务场景总览

场景 入口定位 目标用户 主要终端 核心产物 优先级
场景一：Axure 导入企业研发 首页独立入口：导入已有原型开始项目 企业产品经理、研发经理、测试经理、交付经理 PC Web 为主，移动端只做查看与审批 导入工作区、DSL 基线、需求追溯、测试意图、开发任务、Harness 交付包 P0
场景二：人工澄清自动研发 首页独立入口：一句话需求开始，人工确认各阶段 有明确项目意向的个人用户、创业团队、企业内部小系统负责人 移动端入口优先，PC Web 承接详情编辑 项目基线、需求基线、原型、代码、测试、部署记录 P1
场景三：全自动行业产品 首页独立入口：选择行业或一句话生成通用成品 没有明确沟通意愿、只要通用行业软件的用户 移动端入口优先，PC Web 做预览与接管 行业模板实例、自动生成应用、沙箱预览、质量报告 P2

1.2 场景一：Axure 导入企业研发

这是 To B 主战场。用户不是从“想法”开始，而是已经有项目基线、需求基线和 Axure 原型，平台要承担从原型资产到工程交付的企业级转换、治理和执行。

目标对齐

  • 把 Axure/Figma/HTML 原型从静态资料变成可追溯、可测试、可开发、可部署的 AI RD 工作区。
  • 将原型页面、组件、交互、业务流程映射到 DSL，再由 DSL 生成测试意图、开发任务和部署合同。
  • 保留企业用户的人工确认、审批、版本基线、审计和回滚能力。

端到端链路

导入准备：创建企业原型导入工作区，选择项目、版本、业务域、导入源和环境。
原型解析：解析 Axure HTML ZIP、页面层级、组件、交互链接、表单、表格、弹窗和资源。
DSL 转换：生成 prototype_dsl、page_dsl、flow_dsl 和初始 test_intent_dsl。
人工确认：页面树、组件识别、流程边、需求映射、排除范围和优先级确认。
研发执行：生成实现计划、代码任务、自动化测试、缺陷闭环和交付包。
Harness 交付：基于现有 Harness 能力触发流水线、回写执行结果、生成交付报告。

必须补齐的功能

功能 能力 上游 下游 优先级
独立首页入口 入口明确标识“导入已有原型开始企业研发”，不与一句话需求混用。 首页导航、权限、项目列表 AI RD 工作区 P0
导入解析与确认台 文件上传、解析状态、页面树、组件识别、交互识别、原型预览、确认写入 DSL。 Axure/Figma/HTML 资产 DSL 版本、工作区页面 P0
需求追溯映射 页面/组件/流程边绑定需求、验收标准、优先级和业务规则。 需求基线、导入页面 测试意图、开发任务、交付报告 P0
企业交付门禁 检查 DSL 完整性、需求覆盖率、测试覆盖率、代码任务状态、Harness 可交付状态。 DSL、测试、开发、部署配置 交付包、Harness handoff P0
企业审计与回滚 DSL 版本 diff、版本回滚、导入批次审计、人工确认记录、交付包快照。 工作区操作 治理报告、问题追责 P0

1.3 场景二：人工澄清自动研发

该场景从一句话需求开始，但用户愿意确认项目和需求。它适合作为 To C 或轻量团队产品入口，移动端是主要触达入口，PC Web 做深度编辑和交付查看。

链路

一句话需求 -> 人工澄清项目 -> 人工澄清需求 -> 自动需求分析 -> 自动出原型 -> 自动开发 -> 自动测试 -> 自动部署发布

需要与 DSL 的关系

  • 项目澄清结果进入 project_dsl。
  • 需求澄清结果进入 requirement_dsl。
  • 自动原型进入 prototype_dsl/page_dsl。
  • 自动测试进入 test_intent_dsl。
  • 自动开发进入 implementation_dsl。
  • 自动部署进入 delivery_dsl。

优先实现范围

P1移动端入口

移动端首页突出“一句话创建应用”，以卡片式问答和阶段状态为主，不承载复杂编辑器。

P1人工确认门禁

项目基线、需求基线、原型确认、开发执行、部署发布均要有确认点，避免 AI 直接越权执行高风险动作。

1.4 场景三：全自动行业产品

这个场景当前平台 AI 会话已经具备一部分“从需求到成品”的能力，但要产品化，必须补行业模板、沙箱隔离、自动评测和发布门禁。

链路

一句话/行业选择 -> AI 自动澄清 -> 套用行业模板 DSL -> 自动生成原型/代码/测试 -> 沙箱预览 -> 质量评估 -> 用户接管或发布

行业模板 DSL 是关键

  • 不能让 AI 每次凭空生成行业系统，需要沉淀行业模板：CRM、物业、进销存、工单、审批、人事、资产、内容管理等。
  • 行业模板应包含默认角色、页面、数据模型、流程、测试集、部署建议和合规模板。
  • 该场景优先做移动端轻入口，企业级深度交付仍回到场景一的工作区治理。
架构判断：行业模板和快速出成品能力要作为 AI研发平台的一等入口呈现，但底层不能硬编码在主平台后端。平台负责场景入口、智能体、DSL、治理、审计和交付；生成执行、外部底座适配和重型构建任务应通过独立 Skill Runtime 服务承载；CRUD、表单、流程、报表、驾驶舱、移动端、交付等能力以独立 Skill 插件注册。

可借鉴的生成底座

2.1 DSL 定位

AI研发平台已经存在 page_dsl、system_dsl、recording_flow_dsl、test_intent_dsl 和 AIRdDSLVersion。下一步不是另起炉灶，而是把它们升级为统一的 TestHub AI RD DSL。

边界：本 DSL 只服务【AI研发平台】三条业务场景，不复用、不改造、不依赖“企业原型编辑器 DSL”。两者可以未来做导入适配，但概念和模型必须分开。

DSL 的核心职责

  • 作为 AI 智能体之间的结构化协作协议。
  • 作为前端编辑器、后端服务、测试生成、代码生成、Harness 交付之间的契约。
  • 作为企业审计、版本回滚、需求追溯、交付门禁的证据载体。

2.2 DSL 分层模型

DSL 层 目标 核心字段 主要消费者 优先级

prototype_dsl/page_dsl 表达页面、组件、布局、数据绑定、交互。 pages、components、props、events、actions、responsive 前端编辑器、原型预览、代码生成 P0
flow_dsl/system_dsl 表达页面跳转、业务流程、状态流转、异常路径。 nodes、edges、guards、side_effects、error_handlers 流程图、测试生成、业务分析 P0

2.3 版本、校验与追溯

版本治理

  • 保留现有 AIRdDSLVersion，扩展版本类型：导入基线、人工编辑、AI 生成、测试生成、开发计划、交付基线。
  • 每次关键变更自动生成 DSL snapshot，并支持 diff、rollback、锁定基线。
  • 交付前必须存在一个可追溯的 DSL 版本基线。

Schema 校验

  • P0 先给 workspace_manifest、page_dsl、flow_dsl、test_intent_dsl、delivery_dsl 建 JSON Schema。
  • 保存、同步、导入确认、交付门禁前都必须执行校验。
  • 校验错误需要返回字段路径、错误原因、修复建议，前端以右侧详情面板展示。

追溯链

project_id -> requirement_id -> page_id -> component_id -> flow_edge_id -> test_intent_id -> test_case_id -> code_task_id -> artifact_id -> deployment_id

企业客户最终需要的不是“AI 生成了什么”，而是“每个交付物为什么生成、覆盖了什么需求、经过了哪些测试、由哪个版本发布”。

3.1 三个智能体总览

三个智能体需要独立注册、独立入口、独立编排，但共用 AI RD DSL、会话工作区、测试生成、AI 开发任务、部署与 Harness 能力。

智能体 驱动场景 职责 关键输入 关键输出 优先级
agent_enterprise_prototype_import 场景一 导入解析、DSL 转换、确认任务、需求映射、交付门禁编排。 Axure/Figma/HTML、项目、需求基线、环境 AI RD 工作区、DSL 基线、测试意图、实现计划 P0
agent_supervised_ai_delivery 场景二 项目澄清、需求澄清、阶段确认、自动生成和执行编排。 一句话需求、用户问答、项目约束 项目/需求 DSL、原型、代码任务、测试、部署 P1
agent_autonomous_industry_factory 场景三 行业模板选择、自动澄清、模板实例化、沙箱生成和质量评估。 行业、目标用户、软件类型、少量偏好 行业产品 DSL、可运行成品、评测报告 P2

3.2 企业原型导入智能体

能力边界

  • 只处理 AI研发平台企业原型导入工作区，不操作思源研发管理模块。
  • 不直接把 Axure 变代码，必须先转 DSL、人工确认、生成基线。
  • 高风险动作包括覆盖 DSL 基线、触发开发、触发部署，必须有确认。

编排步骤

  1. 创建或选择企业导入工作区。
  2. 上传并解析原型资产，形成导入候选。
  3. 输出页面树、组件识别、交互边、资源清单和疑点清单。
  4. 用户确认页面、流程、需求映射和排除范围。
  5. 写入 DSL 基线，生成版本。
  6. 生成测试意图、实现计划、开发任务和 Harness 交付计划。

3.3 人工澄清自动研发智能体

这个智能体可以复用当前 AI 会话能力，但要从“对话回答”升级为“阶段化工作流”。每个阶段输出结构化卡片和 DSL 片段，用户确认后才能进入下一阶段。

阶段 智能体行为 用户动作 写入 DSL

3.4 行业产品全自动智能体

该智能体不能完全依赖自由生成，需要行业模板库约束。它的核心不是“聊天更强”，而是“模板、DSL、评测、沙箱、发布门禁”更强。

关键能力

  • 行业模板选择和自动补全。
  • 模板 DSL 实例化。
  • 自动代码生成和沙箱预览。
  • 自动测试评分和安全检查。
  • 用户一键接管到企业工作区，进入场景一的治理体系。

与 Skill Runtime 的关系

行业产品全自动智能体不直接绑定 JEECG、NocoBase、DataEase 等具体平台，也不直接在主平台进程里生成复杂工程。它负责编排：选择模板、补齐业务参数、拆分生成任务、调用 Skill Runtime、接收产物、执行质量门禁、把合格产物写入 AI RD 工作区。

5.1 行业模板与 Skill 工厂能力定位

这块能力要作为【AI研发平台】场景三的核心竞争力建设，但底层实现必须服务化、插件化、适配器化。用户看到的是平台内置的“行业产品快速生成”入口，工程上执行的是独立 Skill Runtime 和外部生成底座适配。

平台内置产品入口与治理

首页入口、场景三工作区、行业模板市场、智能体任务流、质量报告、产物接管、权限、审计、版本、交付包全部留在平台内。

独立服务生成执行与沙箱

模板实例化、Skill 编排、外部底座调用、工程构建、预览、自动测试、失败重试由独立服务承担，支持横向扩展。

Skill 插件能力生态

CRUD、表单、流程、报表、驾驶舱、移动端、集成、部署等能力以 Skill 形式注册，既能平台自研，也能接入外部开源能力。

原则：平台不能变成 JEECG、NocoBase、DataEase 或某个低代码平台的二次封装。外部能力只能作为目标底座或适配器，平台核心资产必须是 AI RD DSL、行业模板 DSL、Skill 契约、治理链路和交付闭环。

5.3 独立 Skill Runtime 规划

Skill Runtime 是“执行层”，不是新的产品入口。它可以独立部署、独立扩容、独立升级，主平台通过标准 API 调用它。

服务能力 目标 接口形态 治理要求
模板匹配与实例化 根据行业、软件类型、规模、终端和用户偏好生成模板实例。 POST /templates/match、POST /templates/instantiate 返回模板版本、缺省项、风险项和可用 Skill 列表。
Skill 编排执行 按计划执行多个 Skill，支持串行、并行、条件分支和失败重试。 POST /runs、GET /runs/{id}、POST /runs/{id}/cancel 每步记录输入摘要、输出摘要、日志、耗时和错误码。
沙箱构建预览 隔离构建生成工程，提供临时预览地址和截图检查。 POST /sandboxes、GET /previews/{id} 容器隔离、资源限制、超时回收、访问令牌。
产物管理 回传源码、配置、页面 DSL、报表定义、测试脚本、部署描述。 GET /runs/{id}/artifacts 产物必须有类型、来源 Skill、hash、大小、预览方式和安全扫描状态。
质量评测 对可运行成品执行冒烟测试、页面可用性、权限、数据模型和安全检查。 POST /evaluations、GET /evaluations/{id} 输出 blocking/warning/pass，阻断项不允许自动发布。
执行回放 根据 generation_manifest 重放一次生成，用于问题排查和模板迭代。 POST /runs/{id}/replay 重放必须绑定原模板版本、Skill 版本和适配器版本。

部署约束

  • 运行时服务建议独立为 testhub-skill-runtime，生成 Worker 独立为 testhub-generator-worker，沙箱预览独立为 testhub-preview-sandbox。
  • 主平台只保存任务状态和最终产物索引，日志大文件和临时构建目录由运行时管理并按策略归档。
  • 每个外部底座适配器必须可启停、可限流、可降级，不能因为一个适配器故障影响平台基础能力。
  • 涉及账号、密码、Token、仓库密钥、部署密钥的内容只能走平台密钥管理，不写入模板 DSL 明文。

5.5 外部底座适配规划

外部平台的接入要采用 Adapter 模式。Adapter 只负责把平台 DSL 编译成目标底座可理解的配置、源码或项目结构，再把产物回传给平台，不能让外部平台反向主导平台信息架构。

适配器准入规则

  • 必须声明许可证、部署方式、运行依赖、数据出境风险和商业使用限制。
  • 必须支持 dry-run，先输出计划、差异和预计产物，再允许真正生成。
  • 必须返回结构化错误，不允许只返回大段日志。
  • 必须支持产物反向导入到平台工作区，不能只停留在外部平台预览。
  • 必须经过沙箱测试、冒烟测试和安全扫描后才能进入“可发布”状态。

模板治理流程

  1. 定义行业模板 DSL：角色、菜单、实体、字段、流程、报表、驾驶舱、测试数据、部署建议。
  2. 为模板绑定 Skill 组合：明确每个模块由哪些 Skill 生成，哪些必须人工确认。
  3. 生成黄金样例：每个模板至少保留一个标准可运行样例，用于回归评测。
  4. 建立质量基线：页面可用、核心流程可走通、数据联动正确、测试可回放、交付包完整。
  5. 开放模板市场：展示模板适用范围、生成耗时、支持终端、目标底座、最近质量评分。
  6. 支持企业接管：用户满意后可一键转入企业工作区，进入需求追溯、开发、测试、Harness 交付主线。

6.1 前端设计与交互约束

关键约束：不能把三条业务场景做成一个大页面平铺所有功能。每条场景需要独立入口、独立向导、独立工作区，内部使用左中右布局、页签、抽屉和步骤状态承载复杂能力。
  • 首页只负责场景选择，不展示复杂表格和全部工具按钮。
  • 场景一采用企业工作台布局：左侧资产树，中间预览/编辑/矩阵，右侧详情/确认/问题处理。
  • 场景二采用移动端优先的卡片式阶段流程，PC 端补充详细编辑。
  • 场景三采用极简行业选择和生成进度，质量报告和接管入口放在结果页。
  • 行业模板市场只展示模板、能力范围、适用场景和生成入口；Skill Registry、Adapter 配置、执行日志放入管理/治理页签。
  • Skill Runtime 执行页使用步骤流、日志抽屉、产物列表、质量报告和失败处理，不把所有 Skill 参数摊在主页面。
  • 所有 DSL 原文展示放到“开发/治理/高级”页签，不让普通用户直接面对大 JSON。
  • 右侧详情面板必须展示字段级问题、追溯关系、影响范围和修复入口。

6.2 后端接口与数据约束

规范 要求 说明
场景隔离 所有工作区必须有 scene_type。 避免 Axure 导入、人工澄清、行业工厂的数据和 UI 混在一起。
DSL 校验 所有写入 DSL 的接口都要走统一 validate service。 保存时返回字段路径和修复建议。
版本基线 导入确认、需求确认、开发执行、部署交付前都生成版本。 关键版本支持 diff 和 rollback。
智能体执行 Agent 只写入本场景允许的对象。 高风险动作需要二次确认和审计。
Harness 集成 交付能力使用现有 Harness connection/handoff。 delivery_dsl 作为 Harness handoff 的标准输入。
Skill Runtime 边界 主平台通过标准 API 调用运行时，不把外部底座依赖硬塞进主平台进程。 运行时只返回执行状态、日志摘要、产物索引和质量报告，平台保存治理事实。
Skill 契约 所有 Skill 必须有 skill_contract_dsl、输入输出 schema、权限声明和质量门禁。 缺少契约的能力不能被智能体自动调用。
外部底座适配 JEECG、RuoYi、NocoBase、DataEase 等全部通过 Adapter 接入。 Adapter 必须可启停、可限流、可 dry-run、可回传产物。

6.3 移动端入口规范

  • 场景二和场景三优先提供移动端入口。
  • 移动端不承载复杂原型编辑器、流程图编辑器和大表格矩阵。
  • 移动端职责是输入、澄清、审批、查看结果、接管到 PC。
  • 移动端所有确认动作必须展示风险、版本摘要和预计影响范围。

7.1 阶段路线图

Phase 0：信息架构与场景入口

拆分三入口，补充 scene_type，定义工作区形态和权限菜单。

Phase 1：DSL 底座

建立 Schema Registry、统一校验、版本扩展、追溯 ID 规范。

Phase 2：企业 Axure 主线

完善导入确认、需求映射、测试意图、实现计划、交付门禁。

Phase 3：企业智能体与 Harness 交付

注册企业原型导入智能体，打通 Harness handoff、执行回写和交付包。

Phase 4：人机协同自动研发与移动端

实现移动端入口、澄清卡片、阶段门禁、自动开发测试部署。

Phase 5：全自动行业产品工厂

建设行业模板 DSL、模板市场、全自动智能体和模板实例化流程。

Phase 6：Skill Runtime 与第一批 Skill

独立部署 Skill Runtime，落地行业模板、数据模型、CRUD、表单、报表、驾驶舱、handoff 第一批 Skill。

Phase 7：外部底座适配与生态扩展

优先接入 JEECG/RuoYi 类代码生成、NocoBase 类业务系统、JimuBI/DataEase 类报表驾驶舱，再扩展 Appsmith、ToolJet、Windmill 等专项底座。

Phase 8：模板评测与商业化运营

建立模板黄金样例、自动评测、评分排行、企业接管、交付包和模板迭代机制。

7.2 验收标准

验收项 标准 优先级
三入口清晰 用户从首页可以明确选择 Axure 导入、人工澄清自动研发、全自动行业产品，路径不混用。 P0
DSL 可校验 核心 DSL 保存、导入、同步、交付前均执行 Schema 校验。 P0
Axure 主线闭环 导入 Axure 后能确认页面/组件/流程，生成 DSL 基线、测试意图、开发计划和交付包。 P0
追溯可证明 至少支持需求到页面、组件、流程、测试、部署的链路查询。 P0
Harness 可交付 能基于 delivery_dsl 生成 Harness handoff，触发或预演流水线，回写结果。 P0
移动端可确认 场景二关键阶段可在移动端输入和确认，但复杂编辑回到 PC。 P1
行业模板可复用 至少沉淀 3 个行业模板 DSL，可实例化为工作区。 P2
Skill 可注册可编排 至少完成行业模板、数据模型、CRUD、表单、报表、驾驶舱、handoff 7 类 Skill 契约和运行记录。 P2
Skill Runtime 可独立运行 生成任务能异步执行、查看日志、取消、重试、回传产物和质量报告，不依赖主平台进程完成重型构建。 P2
外部底座可适配 至少完成 1 个代码生成底座、1 个业务系统 no-code 底座、1 个报表/驾驶舱底座的 dry-run 与产物回传。 P2
行业成品可接管 场景三生成的应用可以一键转入企业工作区，保留模板版本、Skill 执行记录、产物清单和测试报告。 P2

7.3 关键风险与控制

风险 影响 控制方式
DSL 变成巨大 JSON，难以维护 前后端耦合、智能体难复用、版本难 diff。 分层 DSL + schema_version + 引用关系，不做单体 DSL。
三场景入口混乱 用户不知道从哪里开始，企业主线被轻量场景稀释。 首页独立入口，scene_type 隔离，工作区 UI 独立。
Axure 直接生成代码 缺少确认、追溯和审计，企业不可控。 必须先转 DSL、人工确认、生成版本基线，再进入开发。
全自动产品质量不可控 失败率高，影响平台信任。 P2 推进，依赖行业模板、沙箱、自动评测和人工接管。
主平台被生成能力拖重 外部依赖、构建环境和低代码平台适配会让主平台后端臃肿且难升级。 采用独立 Skill Runtime，主平台只保留入口、治理、DSL、审计和产物索引。
绑定单一外部底座 如果只绑定 JEECG 或某个低代码平台，平台核心能力会被外部技术路线限制。 坚持 Adapter 模式，平台 DSL 为主，外部底座只是目标编译器。
Skill 失控调用 智能体可能越权生成、覆盖产物、泄露密钥或触发高风险执行。 Skill Contract 必须声明权限、风险级别、输入输出 schema 和质量门禁，高风险动作走确认和审计。
模板库泛化过度 铺太多行业但没有高质量样例，会导致演示不稳定、交付不可控。 先做高频模板和黄金样例，用自动评测保证模板质量，再逐步扩展行业覆盖。
移动端承载过重 体验差，复杂编辑难用。 移动端只做输入、确认、审批、结果查看，复杂编辑回 PC。
