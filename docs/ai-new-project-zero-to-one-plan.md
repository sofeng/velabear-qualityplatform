# 空仓库新项目 AI 研发 0 到 1 全链路设计与开发方案

## 1. 背景与目标

当前 AI 研发闭环主要适用于“已有项目、已有仓库、已有技术栈”的需求开发场景。对于一个全新的空仓库项目，如果直接进入需求开发和代码生成，会缺少项目愿景、目标端、技术架构、非功能要求、工程脚手架、质量门禁和项目经理过程监督，容易导致后续返工。

本方案补齐“空仓库新项目从 0 到 1”的 AI 研发链路，让 AI 会话在开始写代码前，先通过问答、选择、确认和补充方式沉淀项目基线，再进入脚手架、开发、测试、部署和交付。

## 2. 角色分工

| 角色 | 职责 |
|---|---|
| 用户/项目发起人 | 提供业务目标、目标用户、项目边界、技术约束和优先级确认。 |
| AI 产品经理 | 组织需求澄清、范围拆分、验收标准、业务风险和用户体验要求。 |
| AI 架构师 | 设计技术栈、系统架构、模块边界、数据模型、接口规范、部署拓扑和扩展策略。 |
| AI 测试负责人 | 设计测试策略、质量门禁、自动化测试分层、兼容性矩阵和回归策略。 |
| AI 运维负责人 | 设计容器化、部署环境、持久化、监控、日志、备份、回滚和交付信息。 |
| 资深项目经理 | 贯穿每个阶段做范围、风险、依赖、质量门禁和交付物检查，阻止缺失关键输入时盲目进入下一阶段。 |

## 3. 新项目 0 到 1 全链路

| 阶段 | 输入 | 产出 | PM 监工点 |
|---|---|---|---|
| 1. 项目启动澄清 | 原始想法、业务背景 | 项目愿景、目标用户、成功指标、范围边界 | 是否清楚为什么做、给谁用、做到什么程度算完成。 |
| 2. 目标端与场景确认 | 使用场景、用户角色 | PC/H5/移动端/小程序/API/后台等目标端矩阵 | 是否明确首发端、后续兼容端和不做范围。 |
| 3. 技术架构设计 | 技术约束、团队栈、部署要求 | 架构方案、技术选型、模块边界、数据流 | 是否有可落地技术路线和替代方案。 |
| 4. 非功能基线 | 用户规模、响应目标、安全要求 | 性能预算、兼容性矩阵、安全基线、可观测性要求 | 是否可测试、可验收、可监控。 |
| 5. 数据/API/权限模型 | 业务对象、角色、流程 | 数据模型草案、API 清单、权限矩阵 | 是否支撑核心流程且无明显权限漏洞。 |
| 6. 工程脚手架规划 | 技术选型、仓库信息 | 项目目录结构、依赖清单、命令清单、配置文件计划 | 是否能从空仓库启动、构建、测试。 |
| 7. 脚手架生成与环境验证 | 空仓库、工具链 | 初始化代码、依赖安装、基础运行验证 | 是否留下可复现命令和失败处理记录。 |
| 8. 首个最小需求开发 | 已确认需求和架构 | 最小可用功能代码、单元/接口/UI 测试 | 是否满足验收标准且未越界开发。 |
| 9. 自动化测试与缺陷闭环 | 测试用例、部署环境 | 自动化测试报告、AI 缺陷、修复和回归记录 | 是否所有失败都有归因、缺陷和回归结论。 |
| 10. 容器化部署与交付 | 构建产物、部署目标 | 容器服务、访问地址、账号密码、日志摘要 | 是否可启动、可访问、可回滚、数据可持久化。 |

## 4. AI 会话问答设计

AI 会话在“新项目启动澄清”阶段必须以结构化问答卡片方式输出，不直接写代码。每组问题支持单选、多选、文本补充和确认追加。

### 4.1 项目定位

| 问题 | 类型 | 选项 |
|---|---|---|
| 项目类型是什么？ | 单选 | 管理后台、C 端 Web、移动端应用、小程序、开放 API、数据平台、AI 应用、其他 |
| 首个版本目标是什么？ | 文本 | 由用户补充 |
| 项目成功指标是什么？ | 多选 | 可上线演示、真实用户可用、可接入现有系统、可自动化测试、可容器化部署、可持续迭代 |

### 4.2 目标端与兼容性

| 问题 | 类型 | 选项 |
|---|---|---|
| 首发端是什么？ | 单选 | PC Web、移动 Web、Android、iOS、小程序、API 服务、桌面端 |
| 后续需要兼容哪些端？ | 多选 | Chrome、Edge、Safari、Firefox、移动浏览器、Android、iOS、小程序、第三方 API 调用 |
| 是否需要响应式布局？ | 单选 | 必须、建议、不需要、待确认 |

### 4.3 技术架构

| 问题 | 类型 | 选项 |
|---|---|---|
| 架构形态是什么？ | 单选 | 前后端分离、单体 Web、纯后端 API、微服务、插件化、待 AI 推荐 |
| 前端技术偏好 | 多选 | Vue、React、Next.js、Nuxt、原生 HTML、Element Plus、Ant Design、无偏好 |
| 后端技术偏好 | 多选 | Django、FastAPI、Spring Boot、Node.js、Go、无偏好 |
| 数据存储 | 多选 | MySQL、PostgreSQL、Redis、MongoDB、对象存储、本地文件、待 AI 推荐 |

### 4.4 非功能要求

| 问题 | 类型 | 选项 |
|---|---|---|
| 性能目标 | 单选 | 普通后台、千级日活、万级日活、高并发、待估算 |
| 安全要求 | 多选 | 登录认证、RBAC、数据脱敏、操作审计、接口鉴权、文件安全扫描 |
| 可观测性 | 多选 | 应用日志、错误日志、接口耗时、健康检查、链路追踪、告警 |

### 4.5 工程与部署

| 问题 | 类型 | 选项 |
|---|---|---|
| 仓库模式 | 单选 | GitHub 远程仓库、本地路径仓库、企业 Git、空仓库待初始化 |
| 部署方式 | 多选 | Docker Compose、Kubernetes、单机服务、静态站点、云托管、待 AI 推荐 |
| 数据持久化 | 多选 | 数据库卷、上传文件目录、日志目录、构建产物目录、备份目录 |

## 5. 新增能力清单

| 能力编码 | 类型 | 名称 | 目的 |
|---|---|---|---|
| prompt_new_project_intake | Prompt | 新项目启动澄清 Prompt | 输出问答卡片和首轮项目基线。 |
| prompt_new_project_architecture_design | Prompt | 新项目技术架构设计 Prompt | 生成架构方案、技术选型和模块边界。 |
| prompt_new_project_nonfunctional_baseline | Prompt | 新项目非功能基线 Prompt | 生成性能、兼容性、安全、可观测性、可用性要求。 |
| prompt_new_project_multiplatform_compatibility | Prompt | 新项目多端兼容性 Prompt | 生成目标端矩阵、浏览器/设备兼容策略。 |
| skill_new_project_architecture_review | Skill | 新项目架构评审 Skill | 检查架构完整性、可落地性和风险。 |
| skill_new_project_pm_gate_review | Skill | 新项目 PM 阶段门禁 Skill | 由资深项目经理检查每阶段是否可进入下一步。 |
| agent_new_project_scaffold | Agent | 新项目脚手架 Agent | 在确认后初始化空仓库工程结构。 |
| flow_new_project_zero_to_one | Flow | 空仓库新项目 0 到 1 Flow | 编排从澄清到部署交付的完整链路。 |

## 6. 已落地的数据与执行闭环

为避免 0 到 1 新项目只停留在会话文本里，本阶段新增“空仓库新项目基线”作为后续架构、脚手架、开发、测试和部署的统一输入。

| 能力 | 说明 |
|---|---|
| 新项目启动问答卡片 | 在 AI会话中按项目定位、用户流程、目标端、架构、数据/API/权限、非功能、质量策略、工程部署、项目治理分组确认。 |
| 保存为项目基线 | 将问答答案、追加补充、PM门禁结果、风险登记保存到数据库，形成可审计项目基线。 |
| PM门禁载荷 | 自动记录当前门禁、缺失必填项、下一阶段准入动作和质量门禁。 |
| 风险登记 | 自动识别需求澄清未完成、高并发未量化、架构待推荐等风险，作为后续阶段输入。 |

对应后端数据表为 `assistant_new_project_blueprint`，前端入口在【AI研发平台】-【AI会话】- 选择【本地会话环境】- 选择【新项目启动澄清 Prompt】后返回的问答卡片中。

## 7. 开发实施规划

### Phase 1：方案与能力注册

1. 落地本文档。
2. 新增内置 Prompt/Skill/Agent/Flow 能力。
3. 新增空仓库新项目 0 到 1 Flow 定义。
4. Flow 输出中加入 PM 监工规则和质量门禁。

### Phase 2：AI 会话交互增强

1. 会话能力输出支持 `questionnaire` 结构。
2. 前端渲染问答卡片。
3. 支持单选、多选、文本补充。
4. 支持“确认并追加到输入框”，让用户基于选择结果继续发起下一轮。

### Phase 3：架构与非功能落库

1. 增加项目架构方案、非功能基线、兼容性矩阵、质量门禁记录。
2. 与 AI需求、AI开发项目配置、AI开发环境配置建立关系。
3. 在“文件”页签和 AI 会话中展示相关链路关系。

### Phase 4：脚手架执行器

1. 支持空仓库初始化目录结构。
2. 支持生成依赖、启动命令、测试命令、Dockerfile、compose 模板。
3. 支持本地路径仓库和远程仓库两种模式。
4. 执行前必须经过 PM 门禁和用户二次确认。

### Phase 5：端到端验证

1. 使用空仓库创建新项目。
2. 通过 AI 会话完成问答确认。
3. 生成架构方案和非功能基线。
4. 初始化脚手架、开发最小需求、生成测试、部署并回传访问地址。
5. 每阶段保留 PM 审计日志和交付物清单。

## 8. 验收标准

1. AI 会话选择“新项目启动澄清 Prompt”后，必须返回结构化问答卡片。
2. 问答卡片支持单选、多选、补充说明和确认追加。
3. 工具箱能力中能看到新增 Prompt、Skill、Agent、Flow。
4. 选择“空仓库新项目 0 到 1 Flow”后，Flow 步骤必须覆盖从项目启动到部署交付。
5. Flow 每个阶段必须体现资深项目经理监工要求。
6. 中高风险步骤必须阻塞等待确认，不允许直接写代码、提交代码或部署。
7. 整个链路只处理 AI研发平台范围，不读取、不操作思源研发管理模块。
