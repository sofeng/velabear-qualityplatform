# 基线业务逻辑能力：企业级重构方案

> 状态：设计已确认，待开发（用户 2026-07-12 拍板：先出文档+存记忆；视图第一期做全 9 类）
> 关联：`docs/ai-response-display-and-workspace-platform-plan.md`、澄清重构（memory `clarification-precision-issue.md`）
> 定位：`基线业务逻辑` 是「需求基线 → 测试分析/产品实现」之间唯一的**可执行语义骨架**，是"一句话生成非半成品应用"的**信任锚点**。

---

## 0. 一句话结论

当前「基线业务逻辑」是一个**看起来专业的模板填充器**——0 次 LLM、4 个硬编码领域、8 类视图仅前端渲染 1 张流程图。它和刚修好的项目/需求澄清是**同一种病**（死规则 + 领域模板，未落真实语义），但危害更大：它是下游测试与开发的语义骨架，骨架假 → 测试与开发继承的全是假的。本方案用与澄清重构相同的范式（LLM 主推导 + 统一模型 + 真覆盖门禁 + 原子追溯 + 无回退），把它升级为**企业级原子级多视图业务逻辑**。

## 1. 现状真相：声称 vs 实际

主入口 `build_official_business_logic_analysis_output`（`apps/assistant/new_project_runtime.py:3618`）。

| 维度 | Prompt/Skill 声称 | 代码实际 |
|---|---|---|
| 生成方式 | LLM 推导真实业务逻辑 | **0 次 LLM 调用**，纯 Python 规则（`build_business_logic_views` :13963） |
| 领域识别 | 通用、任意行业 | `infer_business_flow_domain` :9939 只认 **4 域**：education/library/collacase/generic |
| 商城小程序结果 | 电商真实流程 | 落 generic 模板，状态机缺省写死 `draft→submitted→processed→closed`（`build_state_machine_model` :14018） |
| 泳道/权限/异常 | 真实规则 | 写死字符串样板（handoffs、`'按角色…数据范围控制'`、4 条固定异常） |
| 质量门禁 | 覆盖校验 | `evaluate_business_logic_analysis_quality` :14120 只查「8 个 key 存在 + flow_score≥80」，模板永远 pass |
| 前端渲染 | 8 类多视图 | X6 只画 **1 张流程图**；另外 7 类视图只是后端 JSON，无对应图形 |

后端产出 8 类模型（`business_logic_views`）：flow_diagram / swimlane_model / state_machine_model / data_flow_model / permission_matrix / exception_compensation_model / report_metric_model / interface_interaction_model + baseline_trace。
前端（`AIDevConversationWorkspace.vue`）：单页签 `基线业务逻辑`（`businessLogic`，位于「需求」组，`基线需求分析` 之后），AntV X6 可编辑画布 + 多画布文件树。**只用 X6，无 mermaid/bpmn/原生泳道**。

下游消费（都 `Prefer business_logic_views`）：AI原型设计、测试分析（`resolve_business_logic_sections_for_testing` :9174）、自动化用例、产品实现。→ **骨架假，下游全假。**

## 2. 多维度审视

### 客户视角
- 商城小程序验证即露馅：拼团/秒杀/库存超卖/订单超时取消，generic 模板一个都产不出。客户一眼判定"这图和我需求无关"。
- 信任连锁崩塌：业务逻辑是客户最能直观判对错的产物，这里假一次，原型/测试/代码全都不信。

### 产品经理视角
- **不原子**：节点是"业务记录/统计报表"聚合词，不是"拼团订单-成团校验""秒杀库存-原子扣减"。
- **不可追溯**：`baseline_trace` 只有 node_count/covered_fields，没有「图元 ← 需求项 ← 用户原话」链路。
- **视图割裂**：8 个模型各建各的，互不校验——流程有"支付"节点，状态机可能没"已支付"态。

### 测试视角
- **无判定覆盖**：`exception_compensation_model` 是 4 条固定样板，产不出"秒杀-库存 0 并发下单""拼团-成团临界最后一人取消"。
- **状态机不可测**：迁移是 `[item for item in transitions if entity in item]` 字符串筛选，非真「状态×事件→状态」迁移表。
- **门禁自欺**：只查 key 存在性 → 永远 pass。门禁通过 ≠ 逻辑正确。

## 3. 企业级原子级业务逻辑：5 条硬标准

1. **原子性**：每节点 = 不可再分的业务动作/状态/实体/规则，命名来自真实语义。
2. **语义真实**：来自项目基线+需求基线+基线需求分析+**用户原话**经 LLM 推导，非领域模板。
3. **跨视图一致**：所有图共享同一「实体/角色/动作/状态」字典，互相闭环校验。
4. **全链可追溯**：每图元 → 需求项 ID → 用户原话，双向可跳转。
5. **可判定覆盖**：每条分支/守卫/异常都是可被测试分析消费的原子测试种子；门禁 = 业务点覆盖率，非 key 存在性。

## 4. 展示决策：单页签 + 视图切换器 + 多张专用图（1 tab, N views）

**否决单图**（流程+状态机+泳道+数据流+ERD 塞一张 = 蜘蛛网）；**否决多顶层页签**（撑爆「需求」组，且它们本是同一逻辑的不同投影）。
**采用**：保留唯一 `基线业务逻辑` 页签，内部加**视图选择器**，每视图配最合适渲染器。

第一期做**全 9 视图**（用户确认）：

| 视图 | 渲染方式 | 现状 | 说明 |
|---|---|---|---|
| 主业务流程图 | X6 流程图/BPMN | ✅有(内容假) | 主干+异常分支+事务边界 |
| 泳道协作图 | X6 泳道(Lane) | ❌有数据无图 | 角色×动作×交接 |
| 状态机图(按实体) | X6 状态图 | ❌有数据无图 | 真「状态×事件→状态」迁移表 |
| 数据流图 DFD | X6 | ❌有数据无图 | 存储+读写流+审计+外部 |
| **实体关系图 ERD** | X6/表格 | ❌**缺失** | 实体+关系+基数(新增) |
| **时序图(集成/API)** | mermaid sequence | ❌**缺失** | 只读渲染，轻量引入 mermaid(新增) |
| 权限矩阵 | 表格(非图) | ❌有数据无表 | 角色×页面×动作×数据域 |
| 规则/决策表 | 表格 | ❌缺失 | 条件×结果，供测试判定覆盖 |
| 异常·补偿 | 表格+流程分支高亮 | ❌有数据无视图 | 校验失败/并发幂等/回滚/重试人工 |

**渲染度分层**：流程/泳道/状态机/DFD/ERD 复用现有 **X6**（无需引重库）；时序图引 **mermaid**（只读、轻量）；权限/规则/异常用**表格**。

## 5. 目标能力架构（四段式，复用澄清重构范式）

**① LLM 主推导（接活跃 writer 模型 DeepSeek，model_config_id=1）**
新增 `generate_business_logic_with_llm`：输入 = 项目基线 + 需求基线 + 基线需求分析 + **用户原话**（双源，与需求澄清对称：基线保广度、原话保深度）。输出**统一语义模型**（共享实体/角色/动作/状态/规则字典）。模型不可用 → **直接报错，不回退模板**（`ClarificationModelUnavailableError` 同款策略）。

**② 统一模型 → 多视图投影 + 跨视图一致性校验**
一套字典派生全部 9 视图。投影后闭环校验：
- 流程节点动作 ⊆ 权限矩阵动作
- 流程/DFD 涉及状态 ⊆ 状态机状态
- DFD 读写实体 ⊆ ERD 实体
- 每条业务规则在流程图有对应判定节点
不一致 = 门禁失败并定位。

**③ 真覆盖门禁（替换假门禁）**
- 广度：项目基线每页面/功能有流程覆盖
- 深度：用户原话每需求点有对应节点（商城逐条核：拼团/秒杀/超卖/超时取消）
- 维度：状态迁移、异常分支、权限边界、数据一致性齐全
缺 → **有限补全 1 轮（最多 2 轮）**，与需求澄清同款 gate。

**④ 原子追溯 + 下游契约**
每图元带 `trace: {requirement_item_id, user_utterance, page/function}`。测试分析改消费「业务逻辑原子测试种子」（每分支/守卫/异常一个种子）；产品实现按视图逐节点追踪落地（页面/API/实体/状态/权限/异常）。

## 6. 杠杆效应

修好后：测试分析自动获得真实分支/状态/异常测试点；产品实现获得逐节点可追踪开发清单；客户第一眼可验真。→ 直接支撑"一句话生成与需求一一对齐、非半成品、近乎无 bug 的应用"。

## 7. 分期落地建议

- **第一期**：后端 LLM 主推导 + 统一模型 + 真门禁 + 9 视图投影数据；前端 9 视图渲染（X6 复用 + mermaid 时序 + 表格）+ 视图切换器 + 追溯跳转。
- **第二期**：跨视图一致性可视化告警、图元↔需求双向高亮联动、可编辑回写统一模型。
- **风险控制**：新逻辑走独立 builder，**不塞进 `build_new_project_suggested_answers` 等共用函数**（澄清重构血泪教训）；测试模式下 `background_execution_enabled()` 返回 False 保同步契约。

## 8. 验证基准（沿用商城小程序黄金用例）

输入："商城小程序，支持多规格商品、拼团、限时秒杀、库存超卖保护、订单超时自动取消"。
通过标准：
- 主流程含拼团/秒杀分支；状态机含 待支付/已支付/拼团中/成团/未成团/待发货/已发货/已完成/已退款 等真实态
- 库存超卖 → 原子扣减节点 + 并发异常补偿；订单超时 → 定时取消迁移
- 覆盖门禁 passed，4 个用户明说需求点逐条命中
- 9 视图跨视图一致性校验通过
