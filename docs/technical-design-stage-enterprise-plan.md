# 技术设计环节：企业级方案（架构/部署/选型/NFR）

> 状态：**已开发（P1 后端引擎 + P2 前端 9 视图，2026-07-13）**。用户 2026-07-12 拍板出独立文档+存记忆、NFR采集两者分场景。
> **选型策略已于 2026-07-13 推翻 §7 的"两层选型库"**：改为**纯 LLM 驱动**——删除硬编码 `TECH_SELECTION_LIBRARY`、删除用库覆盖 `in_library` 的逻辑、删除 prompt 里的选型库注入、删除复杂度阈值启发式。选型是否主流稳妥/是否需人工确认（in_library/risk）完全由 LLM 自判，与项目澄清/需求澄清/业务逻辑保持同构的"LLM 主判、代码不越权设计"原则。
> 姊妹方案：`docs/baseline-business-logic-enterprise-plan.md`（业务骨架）—— 本文是**技术骨架**，二者同构、共享基建

## 0. 一句话结论

当前链条缺失整个"技术设计"段：业务逻辑回答 WHAT，但没有人回答 HOW（技术怎么承载）。`产品实现`阶段因此只能**即兴发挥架构**——单体/微服务、SQLite/MySQL、端适配、并发、实时性全靠猜。这是"一句话生成的应用跑不了真实体量、是半成品"的**第二个结构性根因**（第一个是业务逻辑造假）。本方案补齐 `需求 → 业务设计 → 技术设计 → 编码` 中缺失的第三段。

---

## 1. 缺两层，不是缺几张图

| 层 | 是什么 | 现状 |
|---|---|---|
| **技术约束（输入/驱动）** | 端、用户体量、数据体量、实时性、可用性、合规、私有化、成本、交付周期 = **NFR** | ❌ 未采集，项目/需求澄清只抓功能 |
| **技术设计（产出/骨架）** | 系统架构图、部署图、选型、数据架构、集成时序… | ❌ 完全没有 |

架构图是被约束**逼出来**的，不是拍脑袋画的。所以先补 NFR 采集，再补技术设计。

---

## 2. 插入位置：三基线 + 双骨架

```
项目澄清(+技术约束) → 项目基线 ┐
需求澄清 → 需求基线            ├─→ 基线需求分析 → 基线业务逻辑(业务骨架) ┐
【技术约束】→ 技术基线(NEW)    ┘                                     ├→ 原型
                                      【基线技术设计(技术骨架, NEW)】 ┘ ↓
                                                                   → 测试分析 → 产品实现
```

- 三基线：项目基线 / 需求基线 / **技术基线(NEW)**，都走"LLM 给建议 + 一句话自动接受"，与现有基线对称。
- 双骨架：基线业务逻辑（业务怎么流转）/ **基线技术设计(NEW)**（技术怎么承载）。

**精确插入规则**：
1. 技术约束采集折进`项目澄清`（"商城小程序"已隐含端/生态/体量）。
2. 技术基线(端+选型)必须在`原型`之前（小程序 vs Web 原型不同）。
3. 完整技术架构设计在`基线业务逻辑`之后、`产品实现`之前，可与`原型`并行。

---

## 3. NFR 采集策略（决策：两者分场景）

- **一句话/轻量场景**：LLM 从项目/需求基线**自动推断** 端/体量/生态/实时性/合规，给默认并**自动接受为技术基线**，不给用户加问答轮（与项目/需求基线自动接受同款）。
- **企业/复杂场景**：走**独立"技术约束澄清"环节**，显式问 端/用户体量/数据体量/实时性/可用性/合规/私有化/成本/交付周期，用户逐项确认。
- 场景判定：由复杂度/普适性推断（见 §6），或用户显式要求企业级时进入独立澄清。

**NFR 维度清单（技术基线字段）**：
端(Web/小程序/App/桌面/大屏/API) · 目标用户与角色 · 并发用户量 · 数据体量(行数/存储量/增速) · 实时性(批/准实时/实时) · 可用性SLA · 一致性要求 · 安全合规(等保/GDPR/信创) · 部署形态(SaaS/私有化/混合) · 成本约束 · 交付周期。

## 5. 五视角设计方案

| 视角 | 关注驱动维度 | 对应产出 |
|---|---|---|
| **架构师** | 分层解耦/选型合理/一致性事务/伸缩/技术债/可测试性 | 系统架构图+选型矩阵+数据架构（约束驱动选型，非越先进越好） |
| **客户** | 端/交付周期/成本/私有化信创/合规/避免锁定 | 端适配矩阵+部署+成本+合规清单（结合 private-deploy） |
| **用户** | 并发量/数据体量/实时性/延迟/可用性 | NFR容量预算+性能预算(P95/QPS/峰值倍数)+实时性分级 |
| **运维** | 部署拓扑/可观测/备份恢复/CI-CD/扩缩容/SLA | 部署架构图+运维可观测+发布回滚流程 |
| **产品** | MVP边界/可扩展/多租户/迭代节奏/通用vs定制 | 复杂度分级+架构演进路线(先单体后拆分) |

## 6. 自适应：按复杂度/通用性裁剪深度

| 档位 | 典型 | 技术设计深度 |
|---|---|---|
| **L1 轻量** | 单表 CRUD 小程序/工具 | 单容器默认、选型简版、跳过分库分表/HA，部署图=单机 |
| **L2 中等** | 商城小程序、SaaS 模块 | 全栈+容器+基础缓存/队列+单区高可用+基础可观测 |
| **L3 企业级** | 多租户平台、高并发交易 | 全 8 视图+微服务/分库分表+多区HA+合规+全链路可观测 |

档位由 LLM 从技术基线（体量/实时性/端/合规）自动推断，用户可调。避免给小程序画 K8s 多区（过度设计）。

## 7. 生成方法（决策：~~选型两层~~ → **纯 LLM 驱动**，2026-07-13 修正）

1. **纯 LLM 选型**（推翻原"两层选型库"）：**不设任何固定技术清单**，LLM 按场景（端×体量×实时性×是否私有化×成本）自行选择最合适技术栈，并**自判**是否主流稳妥（`in_library=true`）还是相对小众/有落地风险需人工确认（`in_library=false` 且在 `risk` 里写明理由）。判断权 100% 在 LLM，代码不用死列表覆盖它。→ 与项目/需求/业务逻辑同构，普适通用，避免"Rust/ClickHouse 等正确但小众的选型被误标越界"。
2. **NFR 驱动**：架构与选型由 NFR 逼出来（体量大→缓存、实时秒级→流式/长连接、私有化→排除云托管专有服务），但**这些是写进 prompt 的原则、不是硬编码 if-else 规则**——由 LLM 推理落地。
3. **真覆盖门禁**（保留，与业务逻辑门禁同构，只校验完备性不规定技术）：每端有栈归属、**每个"基线业务逻辑真实建模的领域实体"有存储归属**（非脚手架通用实体）、每实时链路有方案。缺→补全最多 2 轮（同澄清 gate）。
4. **原子追溯**：每个技术决策 → NFR 驱动 → 需求原话。客户问"为什么用 Redis"→答"因为你要求秒杀 5 万 QPS"。
5. **复杂度自适应**：L1/L2/L3 档位**由 LLM 判定**（去掉原规模阈值启发式），仅缺失时回退 L2。避免给小程序画 K8s 多区。
6. **下游契约**：`产品实现`后续应**严格按技术设计蓝图生成代码**（选型/分层/部署锁定），不再即兴发挥 → 生成代码能跑真实体量。

## 9. 验证基准（商城小程序黄金用例）

输入："商城小程序，多规格商品、拼团、限时秒杀、库存超卖保护、订单超时自动取消"。
- 技术基线自动推断：端=微信小程序、体量=中小、实时性=秒杀链路需准实时、部署=容器化、档位=L2。
- 选型矩阵：小程序前端 + 后端 + MySQL + Redis(秒杀库存/防超卖) + 消息队列(超时取消延时任务) —— 每项带 NFR 追溯。
- 部署图=单区容器高可用；数据架构含订单/库存分表建议；集成时序含微信支付回调。
- 门禁 passed，每端/每类数据/每实时链路均有方案且可追溯。
