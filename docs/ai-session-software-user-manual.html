AI 会话生成软件使用手册

本手册面向产品经理、业务人员、需求分析师、测试人员、研发负责人和开发工程师，说明如何从 AI 产品入口创建会话， 通过项目澄清、需求澄清、基线需求分析、业务逻辑、原型、测试设计、设计风格和应用实现，把一句话想法推进为可追溯、可验证的研发产物。

产品定位

AI 会话生成软件不是普通聊天窗口，而是围绕真实软件研发过程组织的 AI 工作台。它把用户输入、文件、Prompt、Skill、Agent、MCP、 会话环境、工作区文件和可运行产物绑定到同一个会话，让每一步产物都能回看、复用和验收。

面向业务入口

业务人员可以从一句话、用户故事、已有原型或普通对话开始，不需要先写完整 PRD。

面向专业研发

平台按项目澄清、需求澄清、需求分析、业务逻辑、原型、测试、实现组织链路，减少“直接写代码”的失控风险。

面向企业治理

会话详情页保留基线、工作区、文件、快照、代码预览、产品预览和执行记录，便于审计、交接和二次迭代。

先选择哪个会话类型

会话类型代表不同用户能力、不同输入成熟度和不同自动化深度。选择正确入口，可以减少后续澄清成本。

会话类型 适合谁 典型输入 平台会做什么
一句话生成应用 希望快速得到可运行产品的业务负责人、售前、产品经理。 “做一个客户反馈管理系统，支持提交反馈、客服处理、分类统计。” 自动串联项目澄清、需求澄清、基线需求分析、基线业务逻辑、原型、测试分析、自动化用例、设计风格和产品实现。
一句话需求 只知道一个用户故事或业务问题，但需要专业需求分析结果的人。 “作为客服主管，我希望能看到超时未处理反馈，以便及时催办。” 先把故事拆成角色、目标、业务对象、规则、异常、验收标准和测试关注点，再沉淀为需求澄清与基线分析。
从需求澄清开始 已有初步需求说明，想跳过从零发散、直接进入确认与基线化的需求人员。 需求片段、会议纪要、待确认需求清单。 围绕需求条目打磨、重写、补充验收点、接受或不接受，并继续生成脑图、业务逻辑、原型和测试。
已有原型图 已有 Axure、HTML 原型、截图或页面说明的产品/交互人员。 原型 ZIP、HTML、截图、页面目录或交互说明。 优先从原型解析页面、组件、入口、状态和业务流，再生成需求分析、测试分析和业务逻辑。
对话 需要探索、咨询、分析资料或临时调用能力的用户。 问题、资料、文件、代码片段、分析请求。 保持通用 AI 对话能力，可手动选择 Prompt、Skill、Agent、MCP、文件和会话对象作为上下文。

五分钟快速开始

  1. 进入 AI 产品 打开平台后进入“AI 产品”，在顶部输入框描述要生成或分析的软件需求。
  2. 选择会话类型 新手或业务人员优先选择“一句话生成应用”；已有用户故事但不急着生成系统时选择“一句话需求”。
  3. 发送需求 需求可以很短，但最好包含业务对象、使用角色、核心处理动作和统计/验收目标。
  4. 进入会话详情 点击生成出的产品会话，进入 AI 会话详情页，在左侧查看链路执行状态，在右侧查看各工作区产物。
  5. 按产物验收 先确认需求澄清和业务逻辑是否符合真实业务，再看原型、测试设计、设计风格和产品预览。

需求澄清：把模糊需求变成可开发基线

需求澄清是本平台最核心的体验入口之一。它不是单纯让 AI 写一段需求说明，而是把需求拆成可选择、可编辑、可追踪、可验收的结构化条目。

单条需求操作

每个需求节点可以查看平台建议、手工编辑、继续打磨、重写、接受需求、不接受需求。重写用于替换当前条目，打磨用于产生更细的子需求或验收点。

批量需求操作

多选需求后可以批量打磨、批量重写或接受需求。适合把用户故事、会议纪要、业务描述一次性整理成可进入研发链路的需求基线。

接受与不接受

接受需求后，该需求会成为后续基线分析、业务逻辑、原型、测试和实现的稳定输入；不接受需求会从保存基线时排除，避免无依据功能进入实现。

进入基线需求分析

已接受需求会继续转为页面、模块、功能、原子功能、验收标准和测试点。脑图节点可用于继续细化测试点，并可同步回需求澄清项。

从“只有用户故事”开始的推荐流程

  1. 选择“一句话需求” 输入用户故事，例如“作为客服主管，我希望查看超时未处理反馈，以便及时催办”。
  2. 让 AI 拆解故事 平台会识别角色、业务目标、触发条件、业务对象、页面功能、规则、异常和验收标准。
  3. 在需求澄清中确认 对 AI 拆出的条目逐项打磨、重写、接受或不接受，把口语化故事变成专业需求。
  4. 生成基线分析和测试种子 接受后的需求会进入基线需求分析，用于生成页面功能、原子功能、追踪矩阵和测试点。

项目澄清：先定边界，再进入研发

项目澄清用于在需求进入实现前确认项目层面的稳定信息。当前已实现能力包括项目范围、角色、业务对象、规则、风险和下一步研发输入的结构化澄清， 以及空仓库新项目综合澄清中的启动澄清、架构约束、非功能基线、多端兼容、质量策略、工程交付和项目治理。

手册只描述当前已落地能力。技术架构设计 Prompt、非功能基线 Prompt、多端兼容 Prompt、架构评审 Skill 等会作为后续推荐能力或可调用能力出现， 不把它们写成项目澄清弹框里已经独立实现的操作入口。

项目源头标准化

把一句话、文件或项目澄清材料抽取为角色、业务对象、页面、功能、状态、规则、数据、接口、报表和权限边界。

项目澄清打磨重写

围绕单个项目澄清项继续细化或替换，输出可选择、可验收、可保存到项目基线的结构化结果。

项目基线沉淀

确认后的项目澄清会保存为项目基线，供后续需求基线、需求分析、业务逻辑、测试分析和产品实现复用。

设计风格：把视觉约束带入开发

设计风格页签位于产品预览前面，用于在开发实现前确定页面风格。开发 Agent 会读取所选风格档案，把 Design Token、页面模板和视觉验收要求写入实现提示。

风格选择

根据软件类型选择风格，例如管理后台优先“企业稳健”，数据运营可选“金融精密”，开发工具可选“工程深色”。

复制研发指令

把选中风格转换为 AI 开发提示，确保后续代码实现遵守色彩、密度、圆角、字体和页面模板要求。

保存设计档案

保存后可在当前会话和后续开发环节复用，形成可追踪的项目设计基线。

AI 工具箱能力

AI 会话可以从工具箱选择不同类型能力。能力不是越多越好，推荐按当前任务选择必要能力，避免上下文过载。

Prompt

适合固定格式的分析、总结、审查、生成任务，例如项目源头标准化、测试分析提示。

Skill

适合带规则、步骤和输出合约的专业能力，例如需求澄清打磨重写、基线需求分析、业务逻辑分析。

Agent

适合需要决策、检查和串联多步动作的能力，例如源头门禁 Agent 用于检查字段完整性和阻塞项。

Flow

适合固定流程编排，例如从澄清、架构、测试、缺陷闭环到部署交付的长链路。

MCP

适合让 AI 安全读取外部上下文或平台上下文，例如只读读取当前会话的项目基线、需求基线和文件摘要。

Tool

适合执行具体工具动作，例如文件、浏览器、测试、部署或工作区相关操作。

生成结果如何验收

企业级 AI 开发不能只看“有没有生成页面”。建议按需求、流程、原型、测试、风格、代码和运行状态逐层验收。

验收层 检查问题 不通过时怎么处理
需求层 需求是否来自当前会话输入？是否有无依据新增？是否覆盖角色、对象、规则、异常和验收标准？ 回到需求澄清，重写或不接受错误需求，再重新生成后续产物。
业务逻辑层 流程图是否描述当前系统真实业务？是否包含状态流转、权限、异常和补偿？ 重新调用基线业务逻辑 Skill，并明确要求读取当前项目/需求基线。
原型层 页面、字段、操作、状态和提示是否能支撑核心业务流？ 回到原型或需求澄清补充页面与交互，再更新测试设计。
测试层 是否覆盖等价类、边界值、状态转换、权限、异常和数据一致性？ 在测试分析中继续细化原子测试点，避免一个测试点验证多个条件。
风格层 实现是否符合所选设计风格、Design Token、页面密度和视觉验收要求？ 回到设计风格页签重新选择或复制研发指令，再让开发 Agent 修正。
运行层 产品预览是否可访问？容器、数据库、接口和持久化是否正常？ 查看产品实现日志、工作区文件和代码预览，定位构建、启动或运行错误。

常见问题与处理

提示“加载工具箱能力失败”

通常是能力资产或会话环境接口加载失败。刷新页面前先确认登录态仍有效；若只影响能力列表，可继续查看已生成产物。

提示“加载会话环境失败”

会话环境加载失败会影响模型、工具和上下文选择。建议重新进入 AI 产品页或会话详情页，确认当前会话环境仍存在。

突然跳到登录页

同一浏览器应共用一套登录态。若仍出现跳转，多数与本地 token 被清空、浏览器隔离配置或刷新失败有关，重新登录后再打开多个页签验证。

业务逻辑图显示不对

先检查图中业务对象和页面是否来自当前会话。如果出现历史系统内容，回到基线业务逻辑环节重新生成，并要求读取当前会话项目/需求基线。

产品实现失败

查看左侧链路失败卡片、AI 消息、代码预览和工作区文件。失败并不影响前序需求、业务逻辑、原型和测试产物继续复用。

不知道该从哪里开始

只想咨询选“对话”；只有故事选“一句话需求”；想快速产出系统选“一句话生成应用”；已有需求选“从需求澄清开始”；已有原型选“已有原型图”。
